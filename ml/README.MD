# ML

Папка `ml/` содержит весь код, эксперименты и артефакты, связанные с машинным обучением.

Структура:

ml/
├── README.md
├── requirements.txt
├── notebooks/
│   └── .gitkeep
├── src/
│   └── .gitkeep
└── models/
    └── .gitkeep


Основная идея разделения:


notebooks/ → исследуем и экспериментируем
src/       → пишем воспроизводимый ML-код
models/    → сохраняем обученные модели


## `notebooks/` — исследования и эксперименты

Здесь находятся Jupyter Notebook (`.ipynb`).

Эта папка нужна для исследования данных, проверки гипотез и быстрых экспериментов.

Например:


ml/notebooks/
├── 01_eda.ipynb
├── 02_baseline.ipynb
├── 03_feature_engineering.ipynb
└── 04_model_experiments.ipynb


Необязательно иметь именно такие notebooks. Это пример понятной структуры.

## Что делать в notebooks

### EDA

EDA = Exploratory Data Analysis.

Здесь изучаем датасет.

Например:

python
df.head()
df.info()
df.describe()


Проверяем:

- какие есть столбцы;
- какие типы данных;
- сколько строк;
- сколько маршрутов;
- сколько остановок;
- какие временные интервалы;
- есть ли пропуски;
- есть ли дубликаты;
- есть ли выбросы;
- как распределён пассажиропоток;
- есть ли зависимость от часа;
- есть ли зависимость от дня недели;
- есть ли сезонность.

Задача EDA — понять:

> С какими данными мы вообще работаем?

### Baseline

После понимания данных строим простую первую модель.

Например:


данные
 ↓
несколько простых признаков
 ↓
LightGBM
 ↓
метрика


Это baseline.

Baseline нужен как точка сравнения для дальнейших экспериментов.

Например:


baseline                 0.60
+ временные признаки     0.64
+ lag features           0.69
+ rolling features       0.71


Без baseline сложно понять, действительно ли новая идея улучшила модель.

### Feature engineering

Здесь можно экспериментировать с признаками.

Например, из времени:


datetime
   ↓
hour
day_of_week
day
month
is_weekend


Для временных рядов могут использоваться lag-признаки:


passengers(t - 1)
passengers(t - 24)
passengers(t - 168)


То есть пассажиропоток:

- час назад;
- сутки назад;
- неделю назад.

Также могут использоваться rolling-признаки:


rolling_mean_3
rolling_mean_24
rolling_mean_168


Конкретные признаки определяются в ходе анализа данных.

### Model experiments

Здесь сравниваем различные модели и параметры.

Например:


Linear Regression
Random Forest
LightGBM
CatBoost
XGBoost


и разные наборы признаков.

## Важное правило для notebooks

Notebook используется для:


исследования
эксперимента
визуализации
проверки гипотезы


Notebook не должен становиться единственным местом, где существует финальный pipeline.

Плохая ситуация:


final_final_v3_REAL.ipynb


и только этот notebook умеет обучить модель.

Хорошая ситуация:


notebook
   ↓
нашли рабочий подход
   ↓
перенесли его в src/


## `src/` — основной ML-код

Здесь находится код, который должен воспроизводить наш ML pipeline.

В процессе разработки структура может стать такой:


ml/src/
├── preprocessing.py
├── features.py
├── train.py
├── predict.py
└── evaluate.py


Создавать все эти файлы заранее необязательно. Они добавляются по мере необходимости.

## `preprocessing.py`

Отвечает за первоначальную обработку данных.

Пример:


data/raw/
   ↓
preprocessing.py
   ↓
data/interim/


Здесь может происходить:

- загрузка файлов;
- приведение типов;
- обработка дат;
- обработка пропусков;
- удаление некорректных записей;
- объединение таблиц;
- привязка маршрутов;
- привязка остановок;
- географическая привязка.

Главное требование:

> Preprocessing должен быть воспроизводимым.

Если удалить `interim/`, мы должны иметь возможность запустить код и получить эти данные заново.

## `features.py`

Отвечает за создание признаков для модели.

Например:


datetime
   ↓
hour
day_of_week
month


или:


passenger_flow
   ↓
lag_1
lag_24
lag_168
rolling_mean_24


Разделение `preprocessing.py` и `features.py` нужно потому, что это разные задачи.

`preprocessing`:

> Приводим исходные данные в нормальное состояние.

`features`:

> Превращаем данные в признаки, полезные модели.

## `train.py`

Отвечает за обучение модели.

Пример pipeline:


data/processed/train.parquet
            ↓
         train.py
            ↓
       обучение модели
            ↓
       ml/models/model


В `train.py` должны постепенно оказаться:

- загрузка train;
- разделение данных;
- создание модели;
- параметры модели;
- обучение;
- оценка;
- сохранение модели.

Цель — чтобы модель можно было обучить повторно без ручного выполнения notebook.

## `predict.py`

Отвечает за получение прогнозов.

Логика:


данные
  +
обученная модель
        ↓
    predict.py
        ↓
    predictions


Именно здесь должна находиться логика, позволяющая взять новую запись и получить прогноз пассажиропотока.

Позже эта часть особенно важна для интеграции модели с backend.

## `evaluate.py`

Отвечает за оценку качества модели.

Например:


y_true
  +
y_pred
  ↓
evaluate.py
  ↓
score


Почему лучше иметь отдельную реализацию метрики?

Чтобы не получилось:


Участник №1 считает метрику одним способом.
Участник №2 немного другим.
Notebook №3 вообще использует другую функцию.


У команды должна быть одна реализация основной метрики соревнования.

## `models/` — обученные модели

Здесь находятся сохранённые модели.

Например:


ml/models/
├── baseline.pkl
├── lgbm_v1.pkl
├── lgbm_v2.pkl
└── model.onnx


Это не исходный код.

Это результат:


train.py
   ↓
обучение
   ↓
model


Пример:


data/processed/train.parquet
             ↓
          train.py
             ↓
     ml/models/lgbm_v1.pkl


Модель затем используется:


ml/models/lgbm_v1.pkl
             ↓
         predict.py
             ↓
         prediction


Модели сейчас не хранятся в Git, потому что они могут занимать много места и являются воспроизводимым результатом обучения.

`.gitkeep` нужен только для сохранения самой директории.

## `requirements.txt` — Python-зависимости

Здесь перечисляются Python-библиотеки, необходимые ML-части проекта.

Например:


pandas
numpy
scikit-learn
lightgbm
pyarrow
matplotlib
jupyter


Устанавливаются они командой:

bash
pip install -r ml/requirements.txt


Это нужно, чтобы все ML-разработчики использовали одинаковый набор библиотек.

Если используем новую библиотеку в проекте — её необходимо добавить в `requirements.txt`.

Не нужно добавлять библиотеку просто потому, что она установлена на компьютере. Добавляем зависимости, которые реально нужны проекту.

## Откуда ML берёт данные

ML-код работает с общей директорией:


data/


Например:


project/
├── data/
│   ├── raw/
│   ├── interim/
│   └── processed/
│
└── ml/
    ├── notebooks/
    ├── src/
    └── models/


То есть не нужно создавать:


ml/data/


и копировать туда датасет.

Все используют один источник данных:


data/


## Как выглядит весь процесс

### Шаг 1. Получаем датасет

Исходные файлы помещаются:


data/raw/


### Шаг 2. Исследуем данные

Используем:


ml/notebooks/


Например:


01_eda.ipynb


### Шаг 3. Строим baseline

Проверяем простую модель и получаем первую метрику.

### Шаг 4. Экспериментируем

Проверяем:

- новые признаки;
- разные модели;
- разные параметры;
- разные способы валидации.

### Шаг 5. Переносим рабочий подход в `src/`

Когда эксперимент оказался полезным, его основная логика переносится из notebook в обычный Python-код.

Получаем:


raw
 ↓
preprocessing
 ↓
interim
 ↓
features
 ↓
processed
 ↓
train
 ↓
model
 ↓
predict


### Шаг 6. Сохраняем модель

Результат обучения помещается:


ml/models/


### Шаг 7. Используем модель

`predict.py` загружает модель и получает прогноз.

Далее этот механизм можно интегрировать с backend.

## Что коммитим в Git

Коммитим:


ml/README.md
ml/requirements.txt

ml/notebooks/*.ipynb
ml/src/*.py


Не коммитим:


ml/models/*
ml/notebooks/.ipynb_checkpoints/


## Самое главное правило

Если совсем коротко:


notebooks/


> Здесь думаем, исследуем и экспериментируем.


src/


> Здесь находится нормальный воспроизводимый код после успешных экспериментов.


models/


> Здесь лежит результат обучения этого кода.


data/


> Здесь лежат данные, с которыми работает этот код.

Вместе:


                    ┌───────────────┐
                    │   notebooks   │
                    │ эксперименты  │
                    └───────┬───────┘
                            │
                       рабочая идея
                            │
                            ▼
data/raw/ ───────→ preprocessing
                            │
                            ▼
                      data/interim/
                            │
                            ▼
                         features
                            │
                            ▼
                     data/processed/
                            │
                            ▼
                          train
                            │
                            ▼
                       models/
                            │
                            ▼
                         predict
                            │
                            ▼
                         прогноз


Главная цель этой структуры — чтобы к концу хакатона модель существовала не только в голове разработчика и не только в одном огромном Jupyter Notebook, а представляла собой понятный и воспроизводимый pipeline.
