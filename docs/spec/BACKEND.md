# ТЗ Backend

Версия 4.2, 26.09.2026. Общие определения и границы: [README](README.md). Потребители API: внешний клиент с ключами route/date/hour, [Frontend](FRONTEND.md) и пакетный импорт результатов [ML](ML.md).

## 1. Цель и сохраняемая архитектура

Развить существующее приложение `web-forecast/app/main.py`. Сохранить FastAPI, каталог `api/`, `repositories/`, `GTFSRepository` и фабрики `create_*_router(repository)`. Бизнес-логику вынести в `services/`, контракты — в `schemas/`. Подключать роутеры с общим префиксом `/api`; не дублировать его внутри прогнозного роутера.

MVP использует гибридную архитектуру: Excel → `GTFSRepository` → память для справочников, PostgreSQL → `ForecastRepository` для истории, прогнозов, нормализации и метрик. CSV — вход пакетного импорта. Файлового runtime-хранилища прогнозов и `active.json` нет. PostgreSQL, SQLAlchemy 2.x, psycopg 3 и Alembic обязательны; PostGIS не требуется.

Границы ответственности:

| Компонент | Ответственность |
|---|---|
| `GTFSRepository` | Чтение Excel, индексы справочника, методы `get_route_directions`, `get_route_stops`, `get_route_geometry` |
| `ForecastRepository` | SQL: runs, факты, прогнозы, статистики и метрики; не читает Excel и не содержит HTTP-ответов |
| `ForecastService` | Выбор run, проверка диапазонов, получение точек и агрегатов, продуктовый каталог |
| `NormalizationService` | Расчёт статистик и производных полей при импорте; не вызывается из GET |
| `MapService` | Справочная геометрия + один запрос прогноза для выбранных маршрутов; без запроса на каждую feature |
| API-роутеры | Валидация параметров, вызов сервисов, DTO и преобразование ошибок в HTTP |

Существующие фабрики справочных роутеров по-прежнему получают `GTFSRepository`; новые получают сервисы. Внедрение `Depends` не является обязательным. Engine/session factory создаются в lifespan, а SQLAlchemy Session — на отдельную операцию/запрос и закрывается после неё. Один общий Session между обработчиками или workers запрещён.

## 3. Настройки и жизненный цикл

Добавить документированные настройки с путями относительно корня проекта:

| Настройка | Значение по умолчанию / назначение |
|---|---|
| `GTFS_EXCEL_PATH` | Существующий Excel в `dataset/spravochniki/`; заменяет жёсткий путь `GTFS_FILE` |
| `DATABASE_URL` | URL PostgreSQL; пароль не хранить в Git и не выводить в логи |
| `WEB_CONCURRENCY` | Число workers, по умолчанию 1; остальные значения проверяются нагрузочным тестом |
| `CORS_ORIGINS` | Явный список origin фронтенда |
| `APP_TIMEZONE` | `Europe/Moscow` |

Чтение конфигурации, загрузка Excel и создание пула SQL выполняются один раз в lifespan каждого процесса. Импорт модуля не должен читать Excel/БД. Справочник кэшируется в памяти; прогнозы читаются из SQL. Публикация нового run видна новым запросам без перезапуска: активный ID разрешается через БД один раз на запрос. Указанный явно run неизменяем. Суммарный размер пулов с учётом workers и CLI должен укладываться в лимит соединений PostgreSQL.

При отсутствии прогноза приложение поднимается: справочники работают, прогнозные запросы возвращают 503 с понятной причиной. Недоступность БД или неприменённая миграция отмечается как degraded: справочные URL остаются доступны, SQL endpoint возвращают 503. Повторное подключение возможно после восстановления БД. Повреждённый обязательный справочник останавливает старт с диагностикой пути, листа и колонок. В логах не выводить строки транзакций, хеши карт и содержимое нарядов целиком.

Сохранить `GET /health` с `status` и `service`; добавить `gtfs=ok|error`, `database=ok|unavailable|schema_mismatch`, `forecast=ok|missing`, `active_run_id`. HTTP 200 означает живой процесс, `status=degraded` допустим при неготовых компонентах. Диагностика БД имеет короткий timeout и не блокирует справочные запросы. `GET /api/ready` возвращает 200 только при загруженном справочнике, доступной БД нужной ревизии Alembic и активном default run, иначе 503. Отсутствие необязательного YEAR не ухудшает readiness. Корневой `/` сохранить.

Для CORS убрать сочетание wildcard origin и credentials. Для MVP без cookie-авторизации использовать `allow_credentials=false`, явные origin, методы GET/POST/OPTIONS и `Content-Type: application/json` для внешнего API.

## 4. Идентификаторы и каталоги

### 4.1. Разделение сущностей

| Поле | Смысл | Тип в новом API |
|---|---|---|
| `route` | Конкурсный номер, например 1 | integer |
| `route_id` | GTFS ID, например `4450` | string |
| `trip_id` | ID маршрутного пути | string |
| `trip_short_name` | Служебная метка, в текущем файле везде `0` | string, не ключ |
| `stop_id` | ID остановки | string |
| `direction_id` | Направление из источника | integer |

Связывать прогноз с GTFS через `route_short_name → route`. Не приравнивать `route` и `route_id`, не фильтровать геометрию только по `trip_short_name`. Текущий `get_trip_stops()` может смешать маршруты при передаче `0`; для новой геометрии нужен метод с `route`/`route_id`, `trip_id` и `direction_id`.

Excel-идентификаторы вида `4450.0` нормализовать к `4450` только при доказанном целочисленном исходном значении; не обрезать произвольные строковые ID. Пустые значения сериализовать в `null`, не в `NaN`.

### 4.2. Два каталога

Существующий `/api/routes` сохраняет смысл каталога GTFS и ответ `{count, routes}`. В текущем Excel номера: `1,2,3,4,5,6,7,10,11,12`.

Добавить `/api/forecast/routes` для фильтров продукта. Всегда возвращать десять конкурсных номеров, включая отсутствующие в Excel. Поля записи:

```json
{
  "route": 17,
  "name": "Трамвай 17",
  "gtfs_route_ids": [],
  "geometry_available": false,
  "forecast_available": true
}
```

Ответ: `{run_id: string|null, count: 10, routes: [...]}`. `forecast_available` относится к указанному/активному run и ложно, если прогноз не загружен. `geometry_available` означает наличие справочной схемы, а не подтверждённую историческую достоверность. Название брать из справочника, при его отсутствии использовать `Трамвай {route}`. Маршруты GTFS вне конкурсного множества не попадают в фильтры прогноза.

## 5. Геометрия и остановки

1. Читать лист `Порядок_с_координатами` с `header=0`; остальные пять листов — с `header=1`, как в существующем репозитории.
2. Проверять колонки `route_id`, `route_short_name`, `trip_id`, `direction_id`, `stop_sequence`, `stop_id`, `stop_name`, `stop_lat`, `stop_lon`, `start_date`, `end_date`, `actual_date`.
3. Для каждой группы `(route, route_id, trip_id, direction_id, start_date, end_date)` сортировать `stop_sequence` численно. Не объединять разные направления/варианты в одну линию.
4. Проверять конечность и диапазоны координат: широта −90…90, долгота −180…180. При конфликте одной позиции остановки сообщать ошибку справочника; не выбирать строку случайно.
5. Строить GeoJSON LineString в WGS84, координаты `[longitude, latitude]`. Линия требует минимум две различные координаты. Точные дубликаты записей допустимо убрать с записью количества в отчёт.
6. Для текущего конкурсного набора схемы есть у `1,5,7,11,12`; у `17,25,26,28,50` их нет. Определять наличие по данным, не создавать искусственные линии.

Вариант геометрии выбирается явно: MVP отображает все варианты поставленного справочника отдельными features. Весь набор обозначается как `geometry_mode="reference"`. Для каждой feature вернуть `valid_from`, `valid_to`, `reference_actual_date` (максимальная дата актуализации её строк) и `geometry_source="stop_sequence"`. Если период не совпадает с выбранной датой, установить `outside_validity_period=true`; иначе false. Даже false не доказывает наличие полного исторического снимка.

Справочник содержит начала действия 11.10.2025, 16.12.2025 и 20.12.2025, а даты актуализации доходят до февраля 2026. Поэтому схема показывается независимо от выбранной даты с явным пояснением. Не терять маршрут на карте молча из-за временного несовпадения и не утверждать точность рельсовой трассы.

Остановки маршрута выдавать как последовательности с полями `route`, `route_id`, `trip_id`, `direction_id`, `stop_sequence`, `stop_id`, `stop_name`, `lat`, `lon`. Одна остановка может встречаться в нескольких направлениях; это не дубликат ошибки. Прогноз по остановке не вычислять.

Для навигации добавить `geometry_id` и `segment_id`. `geometry_id` — стабильный хеш ключа варианта, включая период действия; `segment_id` — `geometry_id` плюс пары соседних `stop_sequence`. Участок — ровно пара последовательных остановок конкретного пути, не предположение о потоке между ними. `stop_id` без варианта/позиции недостаточен, поскольку остановки повторяются. Справочные `/directions` и `/segments` описаны в API ниже; их ID детерминированы для одного snapshot Excel. При замене справочника вернуть новый `reference_version` (checksum Excel), по которому frontend сбрасывает устаревшие selections.

## 6. Импорт и хранение прогноза

### 6.1. Профили импорта

Реализовать CLI `web-forecast/scripts/import_forecasts.py`. Конкурсная команда:

```text
python web-forecast/scripts/import_forecasts.py --input data/processed/submission.csv --profile competition --activate
```

Основной формат: `--delimiter ";"`, `--date-format iso`. `--profile competition` задаёт все 10 маршрутов, период 01.11–31.12.2025, `horizon=month`, `forecast_kind=forecast`, 14 640 строк. `--profile standard` требует `--horizon day|month|year --from YYYY-MM-DD --to YYYY-MM-DD`; проверяется покрытие всех 10 маршрутов и длина из общего ТЗ. YEAR автоматически получает `forecast_kind=scenario`. Параметры должны совпадать с optional metadata, при конфликте импорт отклоняется. Профиль задавать явно: не угадывать его по размеру файла.

Для совместимости с ТЗ 2.0 поддержать явные `--delimiter ","` и `--date-format mdy`: `11/1/2025` означает 1 ноября. Не угадывать порядок месяца и дня. Формат label test `DD.MM.YYYY` обрабатывает preprocessing ML. `--training-end` и `--metadata` необязательны для импорта, но при наличии cutoff должен быть раньше начала прогноза; для day — ровно предыдущим календарным днём. Источник нормализации дополнительно ограничивается этим cutoff. Для YEAR необходимы scenario_assumptions из metadata; один CSV достаточен для day/month, но не для публикации непояснённого годового сценария.

`--actual-batch-id UUID` явно фиксирует источник истории; `--actual-batch-id none` отключает его. По умолчанию один раз в начале импорта выбирается последний успешно импортированный batch по `(imported_at, id)`. Если batch отсутствует или история маршрута не проходит проверку покрытия/временной границы, используется прогнозный fallback с указанной причиной. Выбранный ID сохраняется в run; последующие публикации фактов не меняют уже идущий расчёт.

Последовательность импорта:

1. Прочитать UTF-8/UTF-8 BOM, проверить ровно четыре колонки и их названия.
2. Проверить типы, даты, маршрут, час, конечность и неотрицательность прогноза. Не превращать `1.5` в маршрут 1.
3. Проверить уникальность ключей и точное покрытие ожидаемой сетки. Счётчика строк недостаточно: набор ключей должен совпасть.
4. Сформировать статистику ошибок с номерами строк; ошибочный файл отклонить полностью. Не удалять молча дубликаты и не заменять пропуски нулями.
5. Зафиксировать версию исторических фактов, рассчитать нормализацию вне HTTP.
6. В одной SQL-транзакции сохранить run, строки прогноза и нормализацию; проверить количество/ключи и пометить run `ready`.
7. При `--activate` в той же транзакции обновить активный указатель только его горизонта. Commit публикует целый снимок. Любая ошибка откатывает транзакцию, предыдущий run остаётся активным. Без флага run доступен по UUID, но не меняет default.

### 6.2. Схема PostgreSQL

Миграции находятся в корневом `migrations/`. Номера конкурсных маршрутов проверяются приложением и CHECK-ограничением; внешнего ключа на Excel-справочник нет, поскольку половина конкурсных номеров там отсутствует.

| Таблица | Основные поля и ключи |
|---|---|
| `forecast_runs` | `id uuid PK`, `status importing\|ready`, `profile`, `horizon day\|month\|year`, `forecast_kind forecast\|scenario`, `model_version nullable`, `model_config_hash nullable`, `training_end date nullable`, `generated_at timestamptz nullable`, `imported_at timestamptz`, `forecast_start/end date`, `row_count`, `source_file nullable` (имя, не абсолютный путь), `source_checksum`, `import_fingerprint UNIQUE`, `actual_batch_id nullable FK`, `normalization_version`, `metadata jsonb` |
| `forecasts_hourly` | Составной PK `(forecast_run_id FK, route_number, forecast_date, hour)`, `prediction double precision`, `relative_load`, `relative_load_pct`, `load_index`, `load_category`, `normalization_degenerate` |
| `normalization_stats` | PK `(forecast_run_id FK, route_number)`, `source_type actuals\|forecast`, `actual_batch_id nullable FK`, `period_start/end`, `sample_count`, `q05/q95`, `degenerate`, `fallback_reason nullable`, `algorithm_version`, `calculated_at` |
| `actual_batches` | `id uuid PK`, `source_checksum UNIQUE`, `period_start/end`, `imported_at`, `coverage jsonb`, `quality_report jsonb`; неизменяемая версия подготовленной истории |
| `actual_hourly` | PK `(actual_batch_id FK, route_number, date, hour)`, `boardings bigint nullable`, `observation_status observed\|confirmed_zero\|missing`; missing не считается нулём |
| `model_metrics` | `id uuid PK`, `evaluation_id`, `model_version`, `model_config_hash`, `data_checksum`, `fold_id`, `training_end`, `validation_start/end`, `horizon_days`, `evaluation_role tuning\|holdout`, `slice_type`, `slice_key`, `metric_name`, `value nullable`, `sample_count`, `actual_sum`, `coverage`, `metadata jsonb` |
| `forecast_active_runs` | `horizon PK`, `forecast_run_id UNIQUE FK`, `updated_at`; один активный ready run на горизонт |

`actual_batches` и `forecast_active_runs` — небольшие вспомогательные таблицы для воспроизводимости и согласованности workers. Для actual batch `source_checksum` вычисляется по каноническим данным вместе со статусами наблюдаемости и coverage metadata, поэтому уточнение качества создаёт новую версию. Статистики старого run не меняются после обновления истории. Метрики относятся к оценённой конфигурации и fold, а не к будущим фактам опубликованного run; `forecast_runs.metadata.evaluation_ids` связывает его с проверенными отчётами. Отчёты импортировать до forecast, указанные ID должны существовать и соответствовать `model_config_hash`. Без отчётов список пуст. Добавление связей позднее требует нового run, не меняет metadata старого. Источник обучения/оценки остаётся явно указанным.

CHECK: `hour` 0–23; прогноз и все float-статистики конечны (отдельно исключить NaN/±Infinity), prediction ≥ 0; relative_load 0–1; pct 0–100; index 1–10; категория соответствует индексу; начало периода ≤ конец. `boardings` ≥ 0 для известных значений; `confirmed_zero` требует 0, `missing` требует NULL. Неизвестные actual допускаются, неизвестные forecast запрещены.

Индексы: составной PK прогноза обслуживает run/route/range; дополнительно `(forecast_run_id, forecast_date, hour, route_number)` для ALL/карты. Для actual — PK и индекс `(actual_batch_id, date, hour)`. Метрики — UNIQUE `(evaluation_id, fold_id, slice_type, slice_key, metric_name)`; `slice_key` всегда непустая строка (`all` для общего среза). Все индексы создаются миграцией. Не добавлять отдельный индекс, полностью повторяющий PK.

Суточные/недельные/месячные суммы считаются `SUM(prediction)` по индексированному ограниченному диапазону, а не сохранёнными независимо редактируемыми totals. Поля нормализации предрассчитаны. Полную БД и все runs не загружать в pandas на старте/GET.

### 6.3. Атомарность и повторный импорт

`import_fingerprint` включает хеш канонически отсортированного CSV, batch истории, модельную версию/конфигурацию, training cutoff, профиль/горизонт/вид прогноза, версию нормализации, отсортированные evaluation_ids и scenario_assumptions. Повторный импорт с тем же fingerprint возвращает существующий run. Разные артефакты модели не смешиваются даже при одинаковых числах. Изменение только имени файла/времени импорта не создаёт дубль.

Уникальный fingerprint и транзакционная блокировка публикации одного горизонта обеспечивают безопасный повтор/конкуренцию CLI. Для MVP при занятой блокировке вернуть понятную ошибку повторного запуска. Активировать уже готовый run позволяет отдельная CLI `activate_forecast.py --run-id ...`; она проверяет status/horizon и меняет указатель транзакционно. Смена активного run не влияет на запросы с закреплённым UUID. Не удалять историю автоматически.

Дополнительные CLI: `import_actuals.py --input ... --metadata ...` для `route;date;hour;boardings` и отчёта наблюдаемости; `import_metrics.py --input ...` для проверенного JSON-отчёта; `normalize.py --run-id ... --actual-batch-id ...` для нового run с пересчитанной статистикой. Metadata истории содержит `missing_keys` и `confirmed_zero_keys`; если есть пустые boardings, но нет статусов/покрытия, импорт отклоняется. Неизменяемость касается исходного и производных полей run. Ошибка любой CLI возвращает ненулевой exit code. Исторический импорт не активирует и не пересчитывает прогнозы автоматически.

## 7. Нормализация

Для каждого маршрута отдельно использовать подтверждённую полную часовую сетку выбранного `actual_batch_id` строго до начала прогнозного периода и не позже известного `training_end`. Для конкурсного run это подготовленная история 01.01–31.10.2025. При отсутствии training_end граница — день перед forecast_start, а неизвестный cutoff явно отмечен. Если для маршрута нет пригодной истории, использовать все его прогнозы за текущий run. История передаётся из ML после проверки пропусков; backend не читает многогигабайтные транзакции.

Исторический snapshot должен явно описывать покрытие, восстановленные нули и отсутствующие наблюдения. Не принимать разреженные положительные строки labels за полное распределение фактов. Для непринятой/неполной истории использовать прогнозный fallback с причиной в metadata.

Рассчитать Q05/Q95 линейной интерполяцией: для отсортированного массива длины `n`, позиция `p*(n-1)`, интерполяция соседних элементов. Расчёт фиксируется один раз при импорте, не зависит от фильтров UI.

```python
if q95 <= q05:
    relative_load = 0.5
    relative_load_pct = 50
    load_index = 5
    normalization_degenerate = True
else:
    relative_load = min(1.0, max(0.0, (prediction - q05) / (q95 - q05)))
    relative_load_pct = floor(relative_load * 100 + 0.5)
    load_index = min(10, max(1, floor(relative_load * 10) + 1))
    normalization_degenerate = False
```

Индекс вычислять из исходного `relative_load`, а не округлённого процента. В обычном случае `0.5 → 6`, в вырожденном — явно заданное исключение `5`. Для вырожденного маршрута записать одно предупреждение на run и показывать признак недостаточной вариативности.

| Индекс | `load_category` | Подпись |
|---|---|---|
| 1–2 | `very_low` | Очень низкая |
| 3–4 | `low` | Низкая |
| 5–6 | `medium` | Средняя |
| 7–8 | `high` | Высокая |
| 9–10 | `very_high` | Очень высокая |

В `normalization_stats` сохранять для каждого маршрута Q05/Q95, `source_type=actuals|forecast`, границы источника, число значений, ID версии истории, признак вырожденности и версию алгоритма. Статистику отдавать в metadata run. Проценты не суммировать по часам или маршрутам. Для нового DAY без истории шкала строится по его 24 часам; она не сопоставима со шкалой MONTH автоматически. UI показывает источник и период шкалы.

## 8. Контракт API

### 8.1. Сохранение существующих URL

Сохраняются `/`, `/health`, `/api/routes`, `/api/routes/number/{route_number}`, `/api/routes/{route_id}`, `/api/stops`, `/api/stops/{stop_id}`, `/api/assignments`, `/api/assignments/routes/{route_id}` и их текущие верхнеуровневые формы ответов. Для нарядов `date` остаётся `YYYYMMDD`; синтаксически неверная дата — 422, отсутствие записей — пустой массив и 200. Не смешивать эту дату с ISO-датами прогноза.

Существующий `/api/routes/number/17` может возвращать 404, поскольку это справочник GTFS. Продуктовые фильтры используют новый `/api/forecast/routes`, где 17 обязателен. Неподключённая прогнозная заглушка не является контрактом совместимости.

### 8.2. Новые endpoint

| Метод и путь | Параметры | Ответ |
|---|---|---|
| GET `/api/ready` | — | Готовность справочника, БД и default-прогноза |
| GET `/api/forecast/runs` | `horizon?` | `{active_run_id, active_runs, runs:[RunSummary]}`; при пустой доступной БД — 200 и пустой список |
| GET `/api/forecast/runs/{run_id}` | — | `RunMetadata`, включая нормализацию по маршрутам |
| GET `/api/forecast/runs/{run_id}/metrics` | — | `{run_id, evaluations:[Evaluation]}`; неизвестная метрика не заменяется нулём |
| GET `/api/forecast/routes` | `run_id?` | Продуктовый каталог |
| POST `/api/predict` | JSON-массив ключей; `run_id?` в query | JSON-массив `{route,date,hour,prediction}`, см. §8.5 |
| GET `/api/forecast` | `date`, `route?`, `run_id?` | Почасовые точки дня |
| GET `/api/forecast/point` | `date`, `hour`, `route?`, `run_id?` | Одна точка или по одной точке для каждого маршрута |
| GET `/api/forecast/aggregate` | `from`, `to`, `granularity=day\|week\|month`, `route?`, `run_id?` | Суммы по календарным периодам и маршрутам |
| GET `/api/timeseries` | `from`, `to`, `route?`, `run_id?` | Все почасовые точки диапазона |
| GET `/api/map/routes` | `date`, `hour`, `route?`, `run_id?` | GeoJSON FeatureCollection с прогнозом |
| GET `/api/routes/number/{route}/geometry` | — | Справочный GeoJSON для номера |
| GET `/api/routes/number/{route}/stops` | `trip_id?`, `direction_id?` | `{route, count, stops:[...]}` |
| GET `/api/routes/number/{route}/directions` | — | `{route, reference_version, count, directions:[{geometry_id, trip_id, direction_id, valid_from, valid_to}]}` |
| GET `/api/routes/number/{route}/segments` | `trip_id?`, `direction_id?` | `{route, reference_version, count, segments:[Segment]}` |
| GET `/api/export.csv` | `from`, `to`, `route?`, `hour?`, `run_id?` | CSV с почасовыми строками |

Здесь `route?` — необязательный integer из конкурсного множества. Отсутствие означает ALL; строка `ALL` в HTTP не передаётся. В справочных путях по номеру допустимы номера из объединения конкурсного и GTFS-каталогов. `horizon` у списка runs — необязательный enum `day|month|year`.

Даты в GET — ISO; для POST действуют форматы §8.5. Диапазоны включают обе границы. `from <= to`, максимум 366 дней. `day` — календарные сутки, `week` — неделя с понедельника, `month` — календарный месяц в Europe/Moscow. Крайний неполный период суммирует только запрошенные даты и отмечается `is_partial=true`. При выходе за покрытие run прогнозные endpoint возвращают 422 `OUTSIDE_FORECAST_RANGE`; endpoint не экстраполирует данные. Опубликованный run всегда полный; недостающая ячейка внутри его покрытия — ошибка целостности хранилища и 503, а не нулевой прогноз.

`active_runs` имеет вид `{day: uuid|null, month: uuid|null, year: uuid|null}`. Default `active_run_id` — активный month, иначе day, иначе null; scenario никогда не выбирается автоматически. Фильтр horizon ограничивает `runs`, но не меняет эти указатели. При отсутствующем `run_id` прогнозные запросы выбирают default через БД; если его нет — 503 `FORECAST_NOT_LOADED`. YEAR требует явного UUID. Ready runs сортируются по `imported_at` убыванию, затем ID. При явном неизвестном или неготовом UUID вернуть 404. Не подбирать другой run автоматически под запрошенную дату.

GET JSON/GeoJSON-ответы с прогнозом возвращают фактически использованный `run_id` в теле; CSV и минимальный POST-ответ передают его в заголовке `X-Forecast-Run-Id`. Разрешить чтение этого заголовка через CORS. В начале работы UI выбирает run и далее передаёт его явно. Безопасность снимка между несколькими HTTP-запросами обеспечивает закреплённый UUID, а не время последнего обновления frontend.

### 8.3. Схемы ответов

`RunSummary`: `run_id`, `profile`, `horizon`, `forecast_kind`, `training_end|null`, `forecast_start`, `forecast_end`, `routes` (массив номеров), `row_count`, `imported_at`, `generated_at|null`, `model_version|null`, `timezone`. `RunMetadata` дополняет summary полями `source_checksum`, `actual_batch_id|null`, `normalization_version`, `normalization` (массив статистик раздела 7), `evaluation_ids`, `scenario_assumptions|null`. Для YEAR описание сценарных предположений обязательно при публикации.

`Evaluation`: `evaluation_id`, `model_version`, `model_config_hash`, `data_checksum`, `folds:[{fold_id, training_end, validation_start, validation_end, horizon_days, evaluation_role, slices:[{slice_type, slice_key, sample_count, actual_sum, coverage, metrics:{wape, wape_score, mae, rmse}, metric_notes}]}]`. `metric_notes` — словарь причин по имени метрики. Undefined метрики — `null`; отсутствие отчёта — `evaluations=[]`. Поля coverage и значения вычислены ML, backend проверяет их типы/диапазоны и происхождение. Импорт метрик не меняет прогнозы и не пересчитывает качество из неподтверждённых фактов. Файл `metrics.json` имеет корневую форму `{evaluations:[Evaluation]}`; оболочка HTTP дополнительно содержит run_id и только связанные с ним evaluations.

Общий `ForecastPoint`:

```json
{
  "route": 1,
  "date": "2025-11-01",
  "hour": 8,
  "prediction": 720,
  "relative_load": 0.81,
  "relative_load_pct": 81,
  "load_index": 9,
  "load_category": "very_high",
  "normalization_degenerate": false
}
```

Числа в примере иллюстративные, не результат модели. Формы ответов:

```text
DAY:        {run_id, route: int|null, date, count, points: ForecastPoint[]}
POINT:      {run_id, route: int|null, date, hour, count, points: ForecastPoint[]}
TIMESERIES: {run_id, route: int|null, from, to, count, points: ForecastPoint[]}
AGGREGATE:  {run_id, route: int|null, from, to, granularity: "day"|"week"|"month",
             count, points: AggregatePoint[]}
AggregatePoint: {route, date, period_start, period_end, prediction,
                 hours_count, expected_hours, is_partial}
```

В DAY для одного маршрута 24 точки, для ALL — 240; в POINT — 1 или 10. В aggregate возвращается отдельная сумма каждого маршрута, в том числе в ALL. `date` — начало календарного bucket; `period_start/end` — фактически вошедшие даты, обрезанные запросом; `expected_hours` — число дней этого включительного интервала × 24. `hours_count` обязан ему равняться, иначе 503 целостности. `is_partial` сравнивает интервал с полным календарным bucket. Для day это 24 часа и false. Сортировка массивов: `route`, `date`, `hour`; для агрегатов — `route`, `date`. `route=null` означает запрос всех маршрутов. Для годового графика запрашивать `granularity=month`; полные почасовые массивы нужны только timeseries/CSV, не графику YEAR.

GeoJSON содержит верхнеуровневые `type="FeatureCollection"`, `features`, `run_id`, `date`, `hour`, `reference_version`, `geometry_mode="reference"`. Каждая feature имеет стабильный ID `geometry_id`, `geometry` и `properties`: все поля `ForecastPoint`, а также `route_id`, `trip_id`, `direction_id`, `valid_from`, `valid_to`, `reference_actual_date`, `geometry_source`, `outside_validity_period`. Справочные ответы stops/geometry также содержат `reference_version`; строки stops дополнены `geometry_id`.

`Segment`: `segment_id`, `geometry_id`, `route`, `trip_id`, `direction_id`, `from_stop_id`, `to_stop_id`, `from_sequence`, `to_sequence`, `geometry` (LineString из двух соседних точек). Он не содержит отдельного passenger prediction. У известного маршрута без справочной геометрии directions/segments/stops возвращают пустые массивы. Фильтры географического выбора не применяются к числам в forecast/aggregate/export; этим endpoint передаётся только route.

Для справочного `/geometry` поля прогноза и `run_id` отсутствуют. Для известного маршрута без геометрии — 200, `features=[]`, `geometry_available=false`; `/stops` возвращает пустой массив. Для неизвестного номера — 404. Карта прогноза для известного конкурсного маршрута без схемы также возвращает 200 и пустой FeatureCollection.

### 8.4. Ошибки

Новые endpoint используют `{detail: {code, message, fields?}}`; ошибки валидации схем FastAPI привести к такой же форме. У существующих endpoint допустимо сохранить строковый `detail` для совместимости.

| HTTP | Примеры `code` |
|---|---|
| 422 | `INVALID_REQUEST`, `UNSUPPORTED_ROUTE`, `OUTSIDE_FORECAST_RANGE` |
| 404 | `RUN_NOT_FOUND`, `ROUTE_NOT_FOUND`, `STOP_NOT_FOUND` |
| 503 | `FORECAST_NOT_LOADED`, `FORECAST_STORE_INVALID`, `DATABASE_UNAVAILABLE`, `SCHEMA_NOT_READY`, `SERVICE_NOT_READY` |

Не возвращать traceback или абсолютные пути в HTTP-ответах. В логах сохранять причину для диагностики.

### 8.5. Внешний API прогноза по списку ключей

Это обязательный публичный интерфейс получения прогноза. Клиент передаёт только номер маршрута, дату и час. Подготовка признаков, обучение, выпуск прогноза и его публикация — ответственность системы, а не вызывающего клиента.

```http
POST /api/predict
Content-Type: application/json
```

Тело запроса — непосредственно массив (один элемент тоже передаётся массивом):

```json
[
  {"route": 1, "date": "11/1/2025", "hour": 0},
  {"route": 1, "date": "11/1/2025", "hour": 1}
]
```

Успешный ответ HTTP 200 — непосредственно массив, ровно четыре поля в каждой записи:

```json
[
  {"route": 1, "date": "11/1/2025", "hour": 0, "prediction": 349},
  {"route": 1, "date": "11/1/2025", "hour": 1, "prediction": 349}
]
```

Значения `349` иллюстрируют формат; реализация возвращает фактический результат опубликованной модели, без констант и подмены данными `test_submission.csv`.

Правила контракта:

- `route` — строго integer из десяти конкурсных номеров, `hour` — integer 0–23; boolean и дробные значения запрещены. Поля `prediction`, `stop_id`, GTFS route_id и любые другие поля во входной записи отклоняются как лишние.
- `date` — строка ISO `YYYY-MM-DD` либо `M/D/YYYY` (также с ведущими нулями). Для записи со слешем порядок **месяц/день/год** фиксирован: `11/1/2025` — 1 ноября, `12/1/2025` — 1 декабря. `D/M/YYYY` и `DD.MM.YYYY` этот endpoint не поддерживает. Разбор строгий, без угадывания и календарного переполнения.
- Внутри системы дата нормализуется в ISO/SQL date. В ответе этого POST поле `date` повторяет исходную принятую строку соответствующего элемента, чтобы сохранить внешний табличный контракт. GET endpoint, SQL и submission остаются ISO. Допустим массив со смешанными ISO/MDY строками.
- Сохранять порядок и количество входных элементов. Повторяющиеся ключи возвращаются повторно в соответствующих позициях; это не импорт и не дубликаты в БД. Один запрос может содержать разные маршруты, даты и часы.
- `prediction` — конечное неотрицательное число из run без дополнительного округления. Нормализация/индексы и служебные поля не добавляются в записи этого ответа; для расширенного представления остаются существующие dashboard GET endpoint.
- Допустимы 1–14 640 элементов включительно. Максимальный размер JSON-тела — 2 MiB; пустой массив/превышение числа элементов — 422, превышение размера тела — 413 `REQUEST_TOO_LARGE`. Лимит достаточен для полной конкурсной сетки.
- `run_id` необязателен и передаётся в query, не в каждой записи. Без него применяется общий default из §8.2. Для конкурсной поставки активный month-run обязан покрывать весь ноябрь–декабрь 2025. Все записи ответа читаются из одного run, выбранного один раз в начале запроса.
- Возвращать `X-Forecast-Run-Id` и `X-Forecast-Kind` в заголовках; открыть их через CORS. Минимальному клиенту не требуется предварительно получать run_id. Клиент, сверяющий несколько запросов, закрепляет полученный UUID явно.
- Валидация атомарная: неверная запись отклоняет весь запрос с 422 и `detail.fields` со списком ошибок `{index, field, code, message}`; index — с нуля. Неподдерживаемый номер и дата вне покрытия — ошибки запроса. Неполный/повреждённый опубликованный run — 503, неизвестный явный run — 404; не возвращать частичный успешный массив и не заменять недостающий прогноз нулём.

Реализация: POST-роутер → `ForecastService.predict_points(keys, run_id)` → `ForecastRepository` → PostgreSQL. Репозиторий получает все уникальные нормализованные ключи пакетным SQL-запросом (или фиксированными порциями), затем сервис восстанавливает порядок и дубликаты. Не выполнять SQL/ML-вызов для каждой строки. POST является операцией чтения: не записывает переданные ключи как факты, не активирует run и не переобучает модель.

Предварительный ML-процесс обязан построить реальный прогноз полной сетки ноября–декабря по истории до конца октября. Если такой прогноз ещё не опубликован, сервис возвращает 503 `FORECAST_NOT_LOADED`; готовность продукта при этом не достигнута. Из отсутствия будущего ground truth не следует невозможность обслуживания ключей — значения этих ключей именно предсказываются.

### 8.6. Прогноз выбранного периода на дашборде

Использовать существующие read endpoint: `/api/timeseries?route=1&from=2025-11-15&to=2025-12-05&run_id=...` для почасовых точек и `/api/forecast/aggregate` с теми же границами для свёртки. Все календарные дни диапазона включаются полностью, часы 0–23. Пропуск route означает все десять маршрутов. Выбор 15.11–05.12 даёт 21 день: 504 точки маршрута или 5 040 точек ALL. Произвольный интервал не обязан совпадать с календарным месяцем.

Для MVP разрешён целевой период 01.11–31.12.2025 в пределах закреплённого конкурсного run; выход за покрытие — 422, без молчаливого обрезания. Выбор периода не создаёт run, не использует фактические значения будущего и не пересчитывает прогноз иначе, чем внешний POST для тех же ключей. Карта и почасовые KPI показывают выбранный час внутри диапазона, суммы — весь диапазон с явной подписью.

## 9. Экспорт

`GET /api/export.csv` отдаёт UTF-8 CSV с `;`, заголовком и колонками в порядке:

```text
route;date;hour;prediction;relative_load_pct;load_index;load_category
```

`hour` при наличии отбирает этот час каждого дня диапазона. Без него экспортируются все часы. Фильтры route/run/даты совпадают с API. Использовать `Content-Type: text/csv; charset=utf-8` и `Content-Disposition: attachment` с безопасным именем, включающим диапазон и run. Этот расширенный экспорт не заменяет конкурсный submission из четырёх колонок.

XLSX-экспорт не блокирует MVP. При его добавлении `/api/export.xlsx` использует те же фильтры, snapshot и значения. Для YEAR имя выгрузки и заголовок `X-Forecast-Kind: scenario` обозначают сценарный характер; формат строк остаётся почасовым. Этот заголовок также открыть через CORS.

## 10. Наряды и расписание

Существующие API нарядов оставить доступными, но не связывать число записей с числом работающих вагонов. В текущем файле всего 15 нарядов за 08.02.2026, возможны несколько смен одного вагона; расписание содержит 15 строк только маршрута 1. Поля `vehicle_capacity`/`capacity` содержат категорию `ОБК`, а не числовую вместимость. Эти источники не покрывают прогнозный период и не дают основания для расчёта occupancy.

Новый endpoint расписания и отдельный диспетчерский экран для MVP не обязательны.

## 11. Проверки и поставка

Обязательные проверки:

- POST `/api/predict`: одна/несколько строк, разные маршруты, несмежные даты, сохранение порядка и повторов, строго четыре поля ответа; ISO и MDY с правильной трактовкой `11/1/2025`; пустой массив, лишние поля, неверные типы, даты/часы, неизвестный run, лимиты тела и 14 640 ключей.
- Атомарный отказ POST при одной неверной строке, один run на весь ответ при конкурентной публикации, равенство значений POST/GET/CSV. По запросу ключей не запускаются обучение, полный inference или SQL на каждую строку.
- Период 15.11–05.12, весь ноябрь–декабрь, один день и выход за покрытие: корректное число часов, суммы и отсутствие фактов будущего в источниках прогнозирования.
- До изменения справочного кода зафиксировать regression-тестами `/`, `/health`, routes/by-number/by-ID, stops и assignments, включая формы ответов и отсутствие записей.
- На настоящем PostgreSQL проверить Alembic с пустой БД, ограничения/индексы, rollback невалидного импорта, идемпотентность и конкуренцию публикации. SQLite не заменяет эти проверки.
- Импорт валидных 14 640 строк; отклонение дубликатов, неполной сетки, неподдерживаемого номера, часа 24, отрицательного/NaN/Infinity prediction, неверной даты; старый run сохраняется после отказа.
- DAY на 240 строк, MONTH на заявленный диапазон; YEAR-импорт при реализации расширения требует scenario metadata. Оба явно выбранных формата дат; готовый run виден другим workers после commit без рестарта.
- Нормализация на фиксированном массиве: значения ниже Q05/выше Q95, границы индексов, `0.5 → 6`, вырожденный случай `50%/5/medium`, история и прогнозный fallback.
- DAY содержит 24/240 точек; POINT — 1/10; MONTH совпадает с суммой часов; CSV совпадает с API до округления UI.
- Справочный каталог сохраняется, продуктовый содержит все 10 маршрутов, `route=1` не превращается в `route_id=1`.
- Геометрия не смешивает маршруты с `trip_short_name=0`, направления и варианты; координаты в правильном порядке; маршрут 17 остаётся доступным без линии.
- Корректные ошибки и отсутствие прогноза при живом справочном API; один run во всех частях ответа.
- Географическая навигация не меняет прогноз/суммы; проверены стабильные ID участка, границы частичных недель/месяцев и метрики без отчёта/с undefined WAPE.
- Обновление actual batch не меняет старую нормализацию; чужие model_config_hash/evaluation_ids отклоняются при связывании метрик.

Поставить README запуска, `.env.example`, фиксацию зависимостей, небольшие тестовые данные без сырого датасета и тесты. Существующая команда разработки сохраняет форму:

```text
python -m uvicorn app.main:app --app-dir web-forecast --host 127.0.0.1 --port 8000
```

Для веб-поставки подготовить `docker-compose.yml`: `postgres` с постоянным volume, `backend` с Excel read-only, `frontend` со статической сборкой из корневого `frontend/`. Миграции запускаются отдельной документированной командой `alembic upgrade head` до готовности backend, а не конкурирующим `create_all()` в каждом worker. ML training не запускается при старте web. Предусмотреть `make up/down/logs/migrate/import-forecast/import-actuals/test/frontend-build/benchmark` и эквивалентные прямые команды для PowerShell. Импорт доступен CLI оператору, публичного write API нет.

В README запуска отдельно описать подготовку реального прогнозного run до приёмки API и пример внешнего POST с JSON-файлом ключей. Метод POST здесь читает результаты и не относится к write API. В нагрузочный сценарий добавить POST на 1 и 24 ключа; полный batch на 14 640 ключей измерять отдельно, не смешивая его latency с точечными запросами. Зафиксировать число SQL-запросов batch, чтобы исключить N+1.

После функциональной приёмки добавить `benchmarks/locustfile.py`. Набор: routes, stops, DAY, POINT, aggregate, timeseries, map. Для 1 run на 14 640 строк провести smoke на 20 пользователях, затем отдельные ступени 100/200/300 concurrent users. Для каждой: разогрев 30 секунд, измерение 120 секунд, фиксированные доли запросов, spawn rate и think time в конфигурации. Записать CPU/RAM машины и каждого контейнера, размер данных, workers/пулы, RPS, p50/p95/p99 и долю ошибок по endpoint. Порог p95 ≤ 300 мс и ошибок <1% проверять на согласованной ступени 100 пользователей на 2–4 vCPU/2–4 ГБ RAM; остальные ступени показывают предел. Concurrency не равна RPS. При провале публиковать фактические цифры и причину, не объявлять цель достигнутой. Для GET исключить чтение Excel/CSV, обучение и квантили; SQL-запросы ограничены выбранным run и диапазоном.
