# ТЗ Backend

Версия 3.0. Общие определения и границы: [README](README.md). Потребители API: [Frontend](FRONTEND.md) и пакетный импорт результатов [ML](ML.md).

## 1. Цель и сохраняемая архитектура

Развить существующее приложение `web-forecast/app/main.py`. Сохранить FastAPI, каталог `api/`, `repositories/`, `GTFSRepository` и фабрики `create_*_router(repository)`. Бизнес-логику вынести в `services/`, контракты — в `schemas/`. Подключать роутеры с общим префиксом `/api`; не дублировать его внутри прогнозного роутера.

MVP использует Excel для справочника и файлы прогнозов с готовыми индексами в памяти. PostgreSQL, PostGIS, SQLAlchemy и миграции не являются условием сдачи. При дальнейшем переходе на БД заменяется реализация репозитория, а публичный API сохраняется.

## 2. Задачи по текущему коду

| Место | Требуемое изменение |

| `api/assignments.py` | Сохранить формы ответов и фильтры; явно обозначить справочный характер |
| `api/forecast.py` | Заменить константу и шаг 15 минут на чтение почасового прогноза; убрать обязательные `stop_id`, `p10`, `p90` |
| `gtfs_repository.py` | Нормализовать идентификаторы, добавить проверку необходимых колонок геометрии, составные индексы и кэш сериализованных записей |

Не оставлять ML inference в GET. Excel, CSV и квантили читаются/рассчитываются при подготовке или старте, а не на каждый запрос. В текущем коде методы фильтруют pandas DataFrame на запрос — для целевого состояния подготовить словари/списки заранее.

## 3. Настройки и жизненный цикл

Добавить документированные настройки с путями относительно корня проекта:

| Настройка | Значение по умолчанию / назначение |
|---|---|
| `GTFS_FILE` | Существующий Excel в `dataset/spravochniki/` |
| `FORECAST_STORE_DIR` | `data/processed/forecast_runs/` |
| `ACTUALS_FILE` | Необязательный подготовленный файл истории |
| `CORS_ORIGINS` | Явный список origin фронтенда |
| `APP_TIMEZONE` | `Europe/Moscow` |

Чтение конфигурации и загрузка данных выполняются один раз в lifespan приложения. Импорт модуля не должен требовать чтения Excel. В MVP один процесс Uvicorn хранит неизменяемый снимок активного run; новый импорт вступает в силу после перезапуска процесса. Горячее обновление и синхронизация нескольких workers не требуются.

При отсутствии прогноза приложение поднимается: справочники работают, прогнозные запросы возвращают 503 с понятной причиной. Повреждённый обязательный справочник останавливает старт с диагностикой пути, листа и колонок. В логах не выводить строки транзакций, хеши карт и содержимое нарядов целиком.

Сохранить `GET /health` с `status` и `service`; добавить `reference_loaded`, `forecast_loaded`, `active_run_id`. Это проверка живого процесса, HTTP 200 допустим при `forecast_loaded=false`. Добавить `GET /api/ready`: 200 только при загруженном справочнике и активном валидном прогнозе, иначе 503. Корневой `/` сохранить.

Для CORS убрать сочетание wildcard origin и credentials. Для MVP без cookie-авторизации использовать `allow_credentials=false`, явные origin и необходимые методы GET/OPTIONS.

## 4. Идентификаторы и каталоги

### 4.1. Разделение сущностей

| Поле | Смысл | Тип в новом API |
|---|---|---|
| `route` | Конкурсный номер, например 1 | integer |
| `route_id` | GTFS ID, например `4450` | string |
| `trip_id` | ID маршрутного пути | string |
| `trip_short_name` | Служебная метка, в текущем файле везде `0` | string, не ключ |
| `stop_id` | ID остановки | string |
| `direction_id` | Направление из источника | integer |

Связывать прогноз с GTFS через `route_short_name → route`. Не приравнивать `route` и `route_id`, не фильтровать геометрию только по `trip_short_name`. Текущий `get_trip_stops()` может смешать маршруты при передаче `0`; для новой геометрии нужен метод с `route`/`route_id`, `trip_id` и `direction_id`.

Excel-идентификаторы вида `4450.0` нормализовать к `4450` только при доказанном целочисленном исходном значении; не обрезать произвольные строковые ID. Пустые значения сериализовать в `null`, не в `NaN`.

### 4.2. Два каталога

Существующий `/api/routes` сохраняет смысл каталога GTFS и ответ `{count, routes}`. В текущем Excel номера: `1,2,3,4,5,6,7,10,11,12`.

Добавить `/api/forecast/routes` для фильтров продукта. Всегда возвращать десять конкурсных номеров, включая отсутствующие в Excel. Поля записи:

```json
{
  "route": 17,
  "name": "Трамвай 17",
  "gtfs_route_ids": [],
  "geometry_available": false,
  "forecast_available": true
}
```

Ответ: `{run_id: string|null, count: 10, routes: [...]}`. `forecast_available` относится к указанному/активному run и ложно, если прогноз не загружен. `geometry_available` означает наличие справочной схемы, а не подтверждённую историческую достоверность. Название брать из справочника, при его отсутствии использовать `Трамвай {route}`. Маршруты GTFS вне конкурсного множества не попадают в фильтры прогноза.

## 5. Геометрия и остановки

1. Читать лист `Порядок_с_координатами` с `header=0`; остальные пять листов — с `header=1`, как в существующем репозитории.
2. Проверять колонки `route_id`, `route_short_name`, `trip_id`, `direction_id`, `stop_sequence`, `stop_id`, `stop_name`, `stop_lat`, `stop_lon`, `start_date`, `end_date`, `actual_date`.
3. Для каждой группы `(route, route_id, trip_id, direction_id, start_date, end_date)` сортировать `stop_sequence` численно. Не объединять разные направления/варианты в одну линию.
4. Проверять конечность и диапазоны координат: широта −90…90, долгота −180…180. При конфликте одной позиции остановки сообщать ошибку справочника; не выбирать строку случайно.
5. Строить GeoJSON LineString в WGS84, координаты `[longitude, latitude]`. Линия требует минимум две различные координаты. Точные дубликаты записей допустимо убрать с записью количества в отчёт.
6. Для текущего конкурсного набора схемы есть у `1,5,7,11,12`; у `17,25,26,28,50` их нет. Определять наличие по данным, не создавать искусственные линии.

Вариант геометрии выбирается явно: MVP отображает все варианты поставленного справочника отдельными features. Весь набор обозначается как `geometry_mode="reference"`. Для каждой feature вернуть `valid_from`, `valid_to`, `reference_actual_date` (максимальная дата актуализации её строк) и `geometry_source="stop_sequence"`. Если период не совпадает с выбранной датой, установить `outside_validity_period=true`; иначе false. Даже false не доказывает наличие полного исторического снимка.

Справочник содержит начала действия 11.10.2025, 16.12.2025 и 20.12.2025, а даты актуализации доходят до февраля 2026. Поэтому схема показывается независимо от выбранной даты с явным пояснением. Не терять маршрут на карте молча из-за временного несовпадения и не утверждать точность рельсовой трассы.

Остановки маршрута выдавать как последовательности с полями `route`, `route_id`, `trip_id`, `direction_id`, `stop_sequence`, `stop_id`, `stop_name`, `lat`, `lon`. Одна остановка может встречаться в нескольких направлениях; это не дубликат ошибки. Прогноз по остановке не вычислять.

## 6. Импорт и хранение прогноза

Реализовать CLI `web-forecast/scripts/import_forecasts.py`. Обязательная команда:

```text
python web-forecast/scripts/import_forecasts.py --input data/processed/submission.csv
```

Основной режим: `--delimiter ";"`, `--date-format iso`, период 01.11–31.12.2025, все конкурсные маршруты. Для совместимости с ТЗ 2.0 поддержать явные `--delimiter ","` и `--date-format mdy`: `11/1/2025` означает 1 ноября. Не угадывать порядок месяца и дня. Формат label test `DD.MM.YYYY` обрабатывает preprocessing ML, а не основной submission-контракт.

Последовательность импорта:

1. Прочитать UTF-8/UTF-8 BOM, проверить ровно четыре колонки и их названия.
2. Проверить типы, даты, маршрут, час, конечность и неотрицательность прогноза. Не превращать `1.5` в маршрут 1.
3. Проверить уникальность ключей и точное покрытие ожидаемой сетки. Счётчика строк недостаточно: набор ключей должен совпасть.
4. Сформировать статистику ошибок с номерами строк; ошибочный файл отклонить полностью. Не удалять молча дубликаты и не заменять пропуски нулями.
5. Рассчитать нормализацию, суточные суммы и индексы доступа.
6. Сохранить immutable run с UUID, контрольной суммой, диапазоном дат, количеством строк, временем импорта, необязательной версией модели и нормализацией.
7. Атомарно опубликовать run и указатель `active.json` через временный файл в той же файловой системе. При ошибке предыдущий run остаётся доступным.

Файловый контракт хранилища: `<store>/<run_id>/forecast.csv`, `normalization.json`, `metadata.json`; `<store>/active.json` содержит `run_id`. Нормализованный forecast хранит четыре исходных поля и производные поля из раздела 7. Производные файлы находятся под `data/processed/`, исключённым из Git.

Идемпотентность: одинаковые канонические прогнозы, snapshot истории и версия алгоритма нормализации повторно используют существующий run. Изменение любого из этих компонентов создаёт новый run. Параллельные импорты в MVP запрещены блокировкой с понятной ошибкой; второй процесс не должен перезаписывать активный импорт.

`ForecastRepository` при старте загружает опубликованные runs и создаёт доступ по `(run_id, route, date, hour)`, `(run_id, route, date)` и дневным суммам. Для MVP число хранимых runs ограничивается оператором, начальная поставка — один. Не удалять историю автоматически.

Дополнительные CLI: `import_actuals.py` для `route;date;hour;boardings` и `normalize.py --run-id ...`. Пересчёт не меняет существующий run на месте: публикует новый с новой статистикой. Ошибка любой CLI возвращает ненулевой exit code.

## 7. Нормализация

Для каждого маршрута отдельно использовать всю доступную полную часовую сетку истории до начала прогнозного периода; по умолчанию подготовленную историю 01.01–31.10.2025. Не брать факты из будущего относительно run. Если для маршрута нет пригодной истории, использовать все его прогнозы за текущий run. История передаётся из ML после проверки пропусков; backend не читает многогигабайтные транзакции.

Исторический snapshot должен явно описывать покрытие, восстановленные нули и отсутствующие наблюдения. Не принимать разреженные положительные строки labels за полное распределение фактов. Для непринятой/неполной истории использовать прогнозный fallback с причиной в metadata.

Рассчитать Q05/Q95 линейной интерполяцией: для отсортированного массива длины `n`, позиция `p*(n-1)`, интерполяция соседних элементов. Расчёт фиксируется один раз при импорте, не зависит от фильтров UI.

```python
if q95 <= q05:
    relative_load = 0.5
    relative_load_pct = 50
    load_index = 5
    normalization_degenerate = True
else:
    relative_load = min(1.0, max(0.0, (prediction - q05) / (q95 - q05)))
    relative_load_pct = floor(relative_load * 100 + 0.5)
    load_index = min(10, max(1, floor(relative_load * 10) + 1))
    normalization_degenerate = False
```

Индекс вычислять из исходного `relative_load`, а не округлённого процента. В обычном случае `0.5 → 6`, в вырожденном — явно заданное исключение `5`. Для вырожденного маршрута записать одно предупреждение на run и показывать признак недостаточной вариативности.

| Индекс | `load_category` | Подпись |
|---|---|---|
| 1–2 | `very_low` | Очень низкая |
| 3–4 | `low` | Низкая |
| 5–6 | `medium` | Средняя |
| 7–8 | `high` | Высокая |
| 9–10 | `very_high` | Очень высокая |

В `normalization.json` сохранять для каждого маршрута Q05/Q95, `source_type=actuals|forecast`, границы источника, число значений, checksum истории, `normalization_degenerate` и версию алгоритма. Статистику отдавать в metadata run. Проценты не суммировать по часам или маршрутам.

## 8. Контракт API

### 8.1. Сохранение существующих URL

Сохраняются `/`, `/health`, `/api/routes`, `/api/routes/number/{route_number}`, `/api/routes/{route_id}`, `/api/stops`, `/api/stops/{stop_id}`, `/api/assignments`, `/api/assignments/routes/{route_id}` и их текущие верхнеуровневые формы ответов. Для нарядов `date` остаётся `YYYYMMDD`; синтаксически неверная дата — 422, отсутствие записей — пустой массив и 200. Не смешивать эту дату с ISO-датами прогноза.

Существующий `/api/routes/number/17` может возвращать 404, поскольку это справочник GTFS. Продуктовые фильтры используют новый `/api/forecast/routes`, где 17 обязателен. Неподключённая прогнозная заглушка не является контрактом совместимости.

### 8.2. Новые endpoint

| Метод и путь | Параметры | Ответ |
|---|---|---|
| GET `/api/ready` | — | Готовность справочника и прогноза |
| GET `/api/forecast/runs` | — | `{active_run_id, runs:[RunSummary]}`; при отсутствии runs — 200 и пустой список |
| GET `/api/forecast/runs/{run_id}` | — | `RunMetadata`, включая нормализацию по маршрутам |
| GET `/api/forecast/routes` | `run_id?` | Продуктовый каталог |
| GET `/api/forecast` | `date`, `route?`, `run_id?` | Почасовые точки дня |
| GET `/api/forecast/point` | `date`, `hour`, `route?`, `run_id?` | Одна точка или по одной точке для каждого маршрута |
| GET `/api/forecast/aggregate` | `from`, `to`, `granularity=day`, `route?`, `run_id?` | Суточные суммы по маршрутам |
| GET `/api/timeseries` | `from`, `to`, `route?`, `run_id?` | Все почасовые точки диапазона |
| GET `/api/map/routes` | `date`, `hour`, `route?`, `run_id?` | GeoJSON FeatureCollection с прогнозом |
| GET `/api/routes/number/{route}/geometry` | — | Справочный GeoJSON для номера |
| GET `/api/routes/number/{route}/stops` | `trip_id?`, `direction_id?` | `{route, count, stops:[...]}` |
| GET `/api/export.csv` | `from`, `to`, `route?`, `hour?`, `run_id?` | CSV с почасовыми строками |

Здесь `route?` — необязательный integer из конкурсного множества. Отсутствие означает ALL; строка `ALL` в HTTP не передаётся. В двух справочных путях по номеру допустимы номера из объединения конкурсного и GTFS-каталогов.

Даты — ISO, диапазоны включают обе границы. `from <= to`, максимум 366 дней. `granularity` пока только `day`. При выходе за покрытие run прогнозные endpoint возвращают 422 `OUTSIDE_FORECAST_RANGE`; endpoint не экстраполирует данные. Для MVP опубликованный run всегда полный; недостающая ячейка внутри его покрытия — ошибка целостности хранилища и 503, а не нулевой прогноз.

`run_id` по умолчанию — активный снимок процесса. При явном неизвестном UUID вернуть 404. Каждый JSON/GeoJSON-ответ с прогнозом возвращает фактически использованный `run_id`; CSV передаёт его в заголовке `X-Forecast-Run-Id`. Разрешить чтение этого заголовка через CORS. В начале работы UI выбирает run и далее передаёт его явно.

### 8.3. Схемы ответов

`RunSummary`: `run_id`, `forecast_start`, `forecast_end`, `routes` (массив номеров), `row_count`, `imported_at`, `generated_at|null`, `model_version|null`, `timezone`. `RunMetadata` дополняет summary полями `source_checksum`, `normalization_version`, `normalization` (массив статистик раздела 7).

Общий `ForecastPoint`:

```json
{
  "route": 1,
  "date": "2025-11-01",
  "hour": 8,
  "prediction": 720,
  "relative_load": 0.81,
  "relative_load_pct": 81,
  "load_index": 9,
  "load_category": "very_high",
  "normalization_degenerate": false
}
```

Числа в примере иллюстративные, не результат модели. Формы ответов:

```text
DAY:        {run_id, route: int|null, date, count, points: ForecastPoint[]}
POINT:      {run_id, route: int|null, date, hour, count, points: ForecastPoint[]}
TIMESERIES: {run_id, route: int|null, from, to, count, points: ForecastPoint[]}
AGGREGATE:  {run_id, route: int|null, from, to, granularity: "day",
             count, points: DailyPoint[]}
DailyPoint: {route, date, prediction, hours_count: 24}
```

В DAY для одного маршрута 24 точки, для ALL — 240; в POINT — 1 или 10. В aggregate возвращается отдельная дневная сумма каждого маршрута, в том числе в ALL. `prediction` в `DailyPoint` — сумма 24 часов. Сортировка массивов: `route`, `date`, `hour`; для суточных данных — `route`, `date`. `route=null` означает запрос всех маршрутов.

GeoJSON содержит верхнеуровневые `type="FeatureCollection"`, `features`, `run_id`, `date`, `hour`, `geometry_mode="reference"`. Каждая feature имеет стабильный ID по ключу варианта, `geometry` и `properties`: все поля `ForecastPoint`, а также `route_id`, `trip_id`, `direction_id`, `valid_from`, `valid_to`, `reference_actual_date`, `geometry_source`, `outside_validity_period`.

Для справочного `/geometry` поля прогноза и `run_id` отсутствуют. Для известного маршрута без геометрии — 200, `features=[]`, `geometry_available=false`; `/stops` возвращает пустой массив. Для неизвестного номера — 404. Карта прогноза для известного конкурсного маршрута без схемы также возвращает 200 и пустой FeatureCollection.

### 8.4. Ошибки

Новые endpoint используют `{detail: {code, message, fields?}}`; ошибки валидации схем FastAPI привести к такой же форме. У существующих endpoint допустимо сохранить строковый `detail` для совместимости.

| HTTP | Примеры `code` |
|---|---|
| 422 | `INVALID_REQUEST`, `UNSUPPORTED_ROUTE`, `OUTSIDE_FORECAST_RANGE` |
| 404 | `RUN_NOT_FOUND`, `ROUTE_NOT_FOUND`, `STOP_NOT_FOUND` |
| 503 | `FORECAST_NOT_LOADED`, `FORECAST_STORE_INVALID`, `SERVICE_NOT_READY` |

Не возвращать traceback или абсолютные пути в HTTP-ответах. В логах сохранять причину для диагностики.

## 9. Экспорт

`GET /api/export.csv` отдаёт UTF-8 CSV с `;`, заголовком и колонками в порядке:

```text
route;date;hour;prediction;relative_load_pct;load_index;load_category
```

`hour` при наличии отбирает этот час каждого дня диапазона. Без него экспортируются все часы. Фильтры route/run/даты совпадают с API. Использовать `Content-Type: text/csv; charset=utf-8` и `Content-Disposition: attachment` с безопасным именем, включающим диапазон и run. Этот расширенный экспорт не заменяет конкурсный submission из четырёх колонок.

## 10. Наряды и расписание

Существующие API нарядов оставить доступными, но не связывать число записей с числом работающих вагонов. В текущем файле всего 15 нарядов за 08.02.2026, возможны несколько смен одного вагона; расписание содержит 15 строк только маршрута 1. Поля `vehicle_capacity`/`capacity` содержат категорию `ОБК`, а не числовую вместимость. Эти источники не покрывают прогнозный период и не дают основания для расчёта occupancy.

Новый endpoint расписания и отдельный диспетчерский экран для MVP не обязательны.

## 11. Проверки и поставка

Обязательные проверки:

- Импорт валидных 14 640 строк; отклонение дубликатов, неполной сетки, неподдерживаемого номера, часа 24, отрицательного/NaN/Infinity prediction, неверной даты; старый run сохраняется после отказа.
- Оба явно выбранных формата импорта, повторный импорт без дублирования, перезапуск с тем же активным run.
- Нормализация на фиксированном массиве: значения ниже Q05/выше Q95, границы индексов, `0.5 → 6`, вырожденный случай `50%/5/medium`, история и прогнозный fallback.
- DAY содержит 24/240 точек; POINT — 1/10; MONTH совпадает с суммой часов; CSV совпадает с API до округления UI.
- Справочный каталог сохраняется, продуктовый содержит все 10 маршрутов, `route=1` не превращается в `route_id=1`.
- Геометрия не смешивает маршруты с `trip_short_name=0`, направления и варианты; координаты в правильном порядке; маршрут 17 остаётся доступным без линии.
- Корректные ошибки и отсутствие прогноза при живом справочном API; один run во всех частях ответа.

Поставить README запуска, `.env.example`, фиксацию зависимостей, небольшие тестовые данные без сырого датасета и тесты. Существующая команда разработки сохраняет форму:

```text
python -m uvicorn app.main:app --app-dir web-forecast --host 127.0.0.1 --port 8000
```

Для веб-поставки подготовить Dockerfile backend и Compose с frontend и volume готовых артефактов; обучение выполняется отдельно. Makefile допустим как оболочка, но README должен содержать прямые команды, работающие и из PowerShell. Миграции БД в файловом MVP не нужны.

После функциональной приёмки выполнить один воспроизводимый нагрузочный сценарий: `/forecast/routes`, DAY, POINT, aggregate, timeseries и map; 1 run на 14 640 строк, разогрев 30 секунд, измерение 120 секунд, 20 одновременных пользователей. Записать машину, workers, смесь запросов, достигнутые RPS, p50/p95/p99, долю ошибок, CPU и RAM. Целевой p95 ≤ 300 мс на 2–4 vCPU и 2–4 ГБ RAM; сотни RPS из исходного ТЗ — ориентир для отдельной проверки. Для всех GET исключить чтение файлов, обучение и расчёт квантилей.
