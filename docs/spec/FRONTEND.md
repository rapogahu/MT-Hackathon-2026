# ТЗ Frontend

Версия 4.2, 26.09.2026. Общие определения: [README](README.md). Точные URL и схемы: [Backend, раздел 8](BACKEND.md#8-контракт-api).

## 1. Назначение и размещение

Создать клиент в корневом `frontend/`: React 19, TypeScript, Vite, MapLibre GL JS, ECharts. В репозитории сейчас нет frontend-кода, поэтому перенос файлов не нужен. Клиент получает готовые прогнозы и показатели через FastAPI, базовый префикс `/api`; прямого доступа к PostgreSQL у браузера нет.

Интерфейс русскоязычный. Основной пользователь анализирует прогноз числа посадок по маршрутам и выбирает дату/час для сравнения ожидаемого потока. Нельзя выдавать прогноз за текущие измерения или заполненность вагона.

Предлагаемая структура:

```text
src/
```

Допустимо уточнять названия файлов без изменения контрактов. Нормализация, выбор квантилей и обучение модели не относятся к клиенту.

## 3. Состояние и начальная загрузка

Единое состояние страницы:

```text
run_id
horizon: day | month | year  # класс выбранного выпуска, из metadata
route: number | null       # null = «Все маршруты»
view: DAY | MONTH | PERIOD | YEAR  # YEAR опционален
date: YYYY-MM-DD           # дата карты, KPI и DAY-графика
hour: 0..23                # час карты и KPI
month: YYYY-MM             # диапазон MONTH-графика
from: YYYY-MM-DD           # начало пользовательского периода включительно
to: YYYY-MM-DD             # конец пользовательского периода включительно
granularity: hour | day | week | month
reference_version
geometry_id: string | null  # конкретный вариант пути/направления
stop_selection: {geometry_id, stop_sequence} | null
segment_id: string | null
```

Порядок загрузки:

1. Запросить `/api/forecast/runs`, выбрать default `active_run_id` (month, иначе day), получить его metadata. YEAR не выбирается автоматически.
2. Загрузить `/api/forecast/routes?run_id=...`. Фильтры формируются из продуктового каталога, а не из `/api/routes`.
3. Первоначально выбрать маршрут 1, DAY, первый доступный день run и 08:00. Не выбирать сегодняшнюю дату вне прогнозного диапазона. Если доступны только сценарные runs, показать отдельное действие открытия сценария.
4. Все следующие запросы данных и экспорт отправлять с тем же `run_id`.
5. Загружать карту, график и KPI параллельно; ошибки блоков обрабатывать независимо.

Состояние фильтров отражать в query string страницы. При открытии ссылки проверить значения относительно выбранного run. Неверное значение заменить допустимым с кратким уведомлением; неизвестный run показать как ошибку с действием «Открыть активный прогноз».

Контрол «Выпуск прогноза» показывает класс горизонта, покрытие, время выпуска при наличии и версию модели. Смена выпуска явно меняет `run_id`; выбор DAY/MONTH в контроле «Детализация» сохраняет его. В частности, DAY в конкурсном 61-дневном run — просмотр 24 существующих точек, а не переключение на специальную DAY-модель. В ответе списка `active_runs` позволяет предложить актуальный выпуск каждого горизонта; новая публикация не заменяет уже открытый UUID без действия пользователя. Показывать уведомление «Доступен новый выпуск» при явном обновлении списка.

Смена фильтра отменяет устаревшие запросы или блокирует применение их ответов. Ключ кэша включает endpoint, `run_id`, маршрут, дату/диапазон и час. Быстрая смена часа не должна оставлять KPI от одного часа и карту от другого: пока новый снимок не получен, показывать состояние загрузки соответствующего блока. Переход на новый run сбрасывает связанные кэши и приводит фильтры к его покрытию.

## 4. Фильтры и режим DAY

Маршруты: все десять номеров `1,5,7,11,12,17,25,26,28,50` и «Все маршруты». Отсутствие геометрии не отключает вариант. В HTTP режим ALL передаётся отсутствием параметра `route`.

DAY использует одну дату и час 0–23. График содержит 24 точки выбранного маршрута: X — час, Y — число посадок. Текущий час выделяется; нажатие на точку меняет час карты и KPI.

Tooltip точки:

```text
1 ноября 2025, 08:00–08:59
Маршрут 1
Прогноз посадок: 720
Относительная загрузка: 81%
Индекс: 9/10 — Очень высокая
```

Нуль рисуется на оси как валидное значение. Пропуск/ошибка не превращается в нулевую точку и не интерполируется. В полной поставке пропуск внутри run является ошибкой данных backend.

## 5. Режим MONTH

Выбор месяца задаёт включительный диапазон `from/to` внутри покрытия run. Для неполного месяца показывать фактические границы; не дополнять отсутствующие даты нулями.

Запрашивать `/api/forecast/aggregate?granularity=day`. X — дата, Y — сумма посадок за день. Отдельная ML-модель и клиентское прогнозирование не нужны. Дневные значения брать из backend.

Карта и три KPI остаются снимком на конкретные `date + hour`, подписанным отдельно. При переходе в другой месяц дату карты устанавливать на первый доступный день этого месяца; текущий час сохранять. Нажатие на столбец/точку дня меняет дату карты, сохраняя час. Дневной tooltip показывает дату, маршрут и «Посадок за день»; не показывает почасовой процент как характеристику суток.

### Произвольный период — обязательный сценарий

Добавить режим PERIOD с календарями «С» / «По», выбором детализации и кнопкой «Получить прогноз». Для конкурсного сервиса границы доступны внутри 01.11–31.12.2025 и покрытия выбранного run. Быстрые варианты: «Ноябрь», «Декабрь», «Весь период». DAY и MONTH остаются удобными готовыми представлениями; возможность выбрать 15 ноября–5 декабря обязательна.

`from <= to`; обе границы включительны, по умолчанию запрашиваются все 24 часа каждого дня. Неверный диапазон не отправлять, рядом показать ошибку. Пока пользователь редактирует даты, отличать черновые фильтры от применённых; результаты и экспорт относятся к последнему успешно применённому диапазону. При клике на кнопку выполнить запрос и показать загрузку. Для периода длиннее суток по умолчанию выбрать суточную детализацию; почасовая остаётся доступной.

Почасовой график получает `/api/timeseries`; дневной/недельный/месячный — `/api/forecast/aggregate` с теми же route, from, to и run_id. Ось X почасового графика содержит дату и час, а не повторяющиеся часы 0–23 без даты. ALL поддерживает все десять маршрутов. Для 15.11–05.12 ожидаются 504 почасовые точки одного маршрута или 5 040 точек ALL.

Показать отдельный итог «Прогноз посадок за выбранный период», вычисленный из исходных чисел без двойного суммирования направлений. Карта и существующие KPI остаются снимком на дату/час внутри диапазона. Если выбранная дата карты вышла из нового диапазона, перевести её на первый день диапазона и сохранить час. Не выдавать почасовой индекс загрузки за индекс всего периода.

На странице явно указать: «Прогноз на ноябрь–декабрь 2025 построен по истории до конца октября. Фактические данные за прогнозируемый период недоступны». Кнопка получения прогноза не требует загрузки пользователем будущих данных, submission или признаков. Отсутствие опубликованного прогноза — отдельная ошибка готовности сервиса, а не пустая фактическая история.

Дашборд может использовать расширенные GET endpoint для карты, индексов и агрегатов. Для одинаковых route/date/hour/run_id числа обязаны совпадать с внешним `POST /api/predict`. Не заставлять frontend вычислять модель или отправлять отдельный запрос на каждый час.

### YEAR — опциональное расширение

Пункт YEAR виден как «Экспериментальный / недоступен», пока не опубликован run с `horizon=year` и `forecast_kind=scenario`. Для открытия требуется явно выбрать этот выпуск. Нельзя растянуть 61 день конкурсного run на год или молча повторить его значения.

Годовой график получает `granularity=month`, X — календарный месяц, Y — сумма посадок. Если годовой интервал начинается не первого числа месяца, показывать все затронутые месяцы (их может быть 13), а крайние частичные периоды подписывать по `period_start/end` и `is_partial`. Неполные суммы не выдавать за полный месяц. Карта/KPI остаются снимком на дату/час внутри этого run; клик по месяцу переводит в MONTH того же выпуска.

Обязательная подпись — «Долгосрочный сценарный прогноз». Показывать `scenario_assumptions`, доступный период истории и отсутствие подтверждённой годовой точности. При реализации YEAR добавить отдельный браузерный сценарий; недоступность режима не блокирует MVP.

## 6. Режим «Все маршруты»

1. Карта отображает все доступные схемы конкурсных маршрутов. Цвет каждой линии соответствует собственному прогнозу этого маршрута в выбранный час.
2. DAY-график показывает отдельную серию для каждого из 10 маршрутов; MONTH — отдельные суточные серии. Легенда позволяет временно скрывать серии; это не меняет фильтры экспорта.
3. Показатель «Прогноз посадок за час — все маршруты» равен сумме 10 записей POINT. Запрещено суммировать features карты: один маршрут может иметь несколько направлений.
4. Общий процент и общий индекс не рассчитываются. На этих двух карточках показать «См. по маршрутам»; ниже вывести таблицу 10 маршрутов с посадками, процентом, индексом и доступностью геометрии.
5. Если данные одного из маршрутов отсутствуют из-за ошибки, не подписывать частичную сумму как полный итог; показать недоступность общего KPI.

Клик по маршруту в карте/таблице переключает общий фильтр на него. При наведении достаточно подсветить связанные элементы, без изменения выбранного часа.

## 7. Карта

Использовать GeoJSON backend в MapLibre. Подложка задаётся конфигурацией; указать её источник и отображать требуемую атрибуцию. Ключи доступа не зашивать в код. Если подложка недоступна, остальные данные страницы продолжают работать, блок карты показывает понятную ошибку/повтор.

Вся линия маршрута, включая разные направления, получает один почасовой цвет. Искусственный градиент по остановкам, случайная загрузка и движущиеся вагоны запрещены.

| Категория | Цвет по умолчанию | Подпись |
|---|---|---|
| `very_low` | `#2563EB` | Очень низкая, 1–2 |
| `low` | `#16A34A` | Низкая, 3–4 |
| `medium` | `#CA8A04` | Средняя, 5–6 |
| `high` | `#EA580C` | Высокая, 7–8 |
| `very_high` | `#DC2626` | Очень высокая, 9–10 |

Цвет дополняется текстом и индексом; выбранная линия выделяется толщиной/обводкой. Карта автоматически подбирает границы при первоначальной загрузке или смене маршрута, но не сбрасывает пользовательский масштаб при каждой смене часа.

Обязательные пояснения:

> Прогноз относится к маршруту целиком.
>
> Схема соединяет остановки из предоставленного справочника. Она может отличаться от трассы и состояния сети на выбранную дату.

В popup маршрута показывать номер/название, выбранную дату/час, посадки, процент, индекс, направление, период действия схемы и дату её актуализации. Для `outside_validity_period=true` дополнительно показать «Выбранная дата вне периода действия этой схемы». Не скрывать такое расхождение.

Остановки загружаются для выбранного конкретного маршрута через `/api/routes/number/{route}/stops`. Popup: название, `stop_id`, маршрут, `trip_id`, направление, последовательность. Если рядом приводится прогноз, подпись только «По маршруту целиком». Для ALL остановки можно не выводить до выбора маршрута.

### Географическая навигация

Для выбранного маршрута загрузить `/directions`, `/stops` и `/segments` из справочных URL по номеру. Выбор конкретного пути (`geometry_id`, `trip_id`, направление) ограничивает отображаемые остановки/участки. Остановку идентифицировать парой geometry_id/stop_sequence, участок — segment_id: один stop_id может повторяться в пути.

Выбор остановки центрирует карту и открывает popup; выбор участка выделяет линию между двумя соседними остановками и показывает их названия. Выбор направления/остановки/участка не меняет KPI, forecast-запросы, график или CSV: данные по-прежнему относятся ко всему маршруту. Под фильтром написать «Географический выбор; прогноз — по маршруту целиком».

При смене маршрута или `reference_version` сбрасывать несовместимый выбор. В ALL географические контролы отключены с подсказкой «Выберите маршрут»; для маршрута без геометрии — «Нет данных справочника». Смена даты не превращает справочную схему в исторически подтверждённую геопривязку.

Маршрут без геометрии: оставить график/KPI/экспорт доступными, в карте показать «Геометрия маршрута отсутствует в предоставленном справочнике». Если прогноз действительно загружен, добавить «Прогноз доступен». В ALL пояснить, что карта покрывает только часть выбранных маршрутов.

## 8. KPI и форматирование

Для конкретного маршрута:

- «Прогноз посадок за час»: значение `prediction` и явная дата/час.
- «Относительная загрузка маршрута»: `relative_load_pct%`, tooltip о нормализации внутри маршрута.
- «Индекс загрузки»: `load_index / 10` и русская категория.

Для `normalization_degenerate=true` рядом с процентом/индексом показать «Недостаточная вариативность данных; использовано условное среднее значение». Поля не пересчитывать по отображаемому проценту.

Tooltip загрузки также показывает источник шкалы (`actuals` либо текущий forecast), его даты и предупреждение, что проценты разных выпусков могут использовать разные распределения. Для этого использовать normalization из metadata выбранного run, не вычислять статистику по точкам графика.

Целые посадки в UI форматируются по `ru-RU` с разделением тысяч. При дробном импорте карточки и tooltip округляют неотрицательное число по `floor(x + 0.5)`; CSV сохраняет исходную точность. Суммировать исходные числа до округления. Даты/часы интерпретировать в `Europe/Moscow`, не допускать сдвига даты из-за timezone браузера.

Не использовать подписи «уникальные пассажиры», «сейчас в трамвае», «процент заполнения салона». Сведения о времени генерации выводить только если они есть в metadata; время импорта не выдавать за время обучения.

### Метрики модели

Блок «Качество на исторической проверке» загружает `/api/forecast/runs/{run_id}/metrics`. Показывать модель/конфигурацию, даты обучения и проверки, длину горизонта, роль fold (`tuning`/`holdout`), покрытие, WAPE, WAPE-score, MAE и RMSE. По умолчанию — общий срез; маршруты/часы/пики доступны, если они есть в отчёте. Не усреднять route-WAPE в браузере для получения global WAPE.

При `evaluations=[]` — «Метрики не предоставлены», при null — «Не определена» с причиной. Метрики historical backtest нельзя подписывать как точность выбранного будущего дня; YEAR не получает метку подтверждённого годового качества из 61-дневного backtest. Отсутствие отчёта не блокирует карту и прогноз. Экран «факт против прогноза» отложен до отдельного контракта истории; не рисовать фиктивную фактическую серию.

## 9. Экспорт и обработка состояний

«Скачать CSV» вызывает backend с текущими `route`, `run_id` и применённым диапазоном: один выбранный день в DAY, видимый месяц в MONTH, from/to в PERIOD, весь сценарный период в YEAR. По умолчанию экспорт содержит все часы диапазона; рядом явно написать «Все часы выбранного периода». Отдельный переключатель «Только выбранный час» добавляет параметр `hour`. Скрытие серий легендой и выбор географического участка не меняют состав экспортируемых маршрутов.

Кнопку блокировать на время запроса, ошибку загрузки показать текстом. Не генерировать CSV из округлённых данных графика. Не называть расширенный CSV конкурсным submission.

YEAR-выгрузку подписать «Скачать сценарный прогноз». XLSX — опционально после реализации серверного endpoint, с теми же фильтрами; кнопку не показывать до его доступности.

| Состояние | Поведение |
|---|---|
| Загрузка | Индикатор/скелетон в соответствующем блоке |
| Нет опубликованного run | Сообщение «Прогноз ещё не загружен», данные не подменяются демо-числами |
| Нет геометрии | Работают график, KPI и экспорт |
| API/сеть недоступны | Понятная ошибка и действие «Повторить» |
| Дата вне диапазона | Ограничение календаря; при ответе 422 показать допустимый период |
| Устаревший запрос | Его ответ не применяется к текущим фильтрам |
| Частичная ошибка блоков | Исправные блоки остаются доступными, ошибочный явно помечен |
| Нулевой прогноз | Показать `0`, не «Нет данных» |

Демонстрационные fixtures допустимы для разработки и тестов в отдельном явном режиме. Production-сборка не включает автоматическую подмену API тестовыми прогнозами.

## 10. Доступность и приёмка

Фильтры и экспорт доступны с клавиатуры, имеют текстовые подписи; ошибки доступны скринридеру. Важная информация карты доступна также в KPI/таблице. На ширине 360 px блоки располагаются вертикально, фильтры и показатели не требуют горизонтальной прокрутки страницы; таблица может прокручиваться внутри собственного контейнера. Проверить также desktop от 1280 px.

Критерии приёмки:

- Видны все десять маршрутов, включая №5 и пять без геометрии; справочные 2/3/4/6/10 не появляются среди прогнозных фильтров.
- DAY/POINT, MONTH и ALL соответствуют API; одинаковые `run_id`, дата и час используются в связанных блоках.
- PERIOD принимает произвольные включительные границы ноября–декабря; проверены один день, переход между месяцами и все 61 день, неверный диапазон, его итог и экспорт. API, POST-прогноз и график дают одинаковые числа на одних ключах.
- Переключение детализации не переключает выпуск; появление нового active run не смешивает старые и новые данные. YEAR недоступен без отдельного сценарного run.
- Карта и все её направления окрашены по показателю всего маршрута; отсутствующие линии не придуманы.
- MONTH считает посадки за день, а карта/KPI остаются явно почасовыми.
- Быстрая смена фильтра не возвращает старые данные; URL восстанавливает выбранное состояние.
- Проверены нулевой прогноз, отсутствие run, отсутствие геометрии, ошибки сети, вырожденная нормализация и исторически несовпадающая схема.
- Экспорт содержит ожидаемые маршруты/период/часы и совпадает с серверными значениями.
- Direction/stop/segment изменяют только географическую навигацию; метрики корректно подписаны и различают ноль, undefined и отсутствие отчёта.
- Проходят TypeScript-проверка и production-сборка; основные пользовательские сценарии проверены в браузере.

Поставить `frontend/package.json` со скриптами `dev`, `build`, `preview`, проверкой типов и тестами, lockfile, `.env.example` с адресом API/настройкой карты, README локального запуска и Dockerfile для Compose. Секреты не хранить в frontend-переменных. Зафиксировать браузерные проверки на малом тестовом наборе и интеграционный сценарий с реальным импортом в PostgreSQL. Сборка frontend не запускает ML и миграции БД.
