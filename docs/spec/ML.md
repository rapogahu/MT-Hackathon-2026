Версия 4.2, 26.09.2026. Общий контракт результата: [README, раздел 6](README.md#6-общий-контракт-ml--backend). Импорт и нормализация: [Backend](BACKEND.md).

## 1. Цель

Создать воспроизводимый pipeline, прогнозирующий число посадок на трамвайный маршрут за календарный час. Подготовить `submission.csv` для периода 01.11–31.12.2025: десять маршрутов, 61 день, 24 часа, ровно 14 640 уникальных строк.

```text
target = boardings(route, date, hour)
       = число событий validation_result == 1
```

`route` извлекается из `ngpt_route`. Считать события посадок, а не уникальные `crd_hashcode`, заполненность вагона или поток на остановке. Модель работает пакетно и не вызывается из HTTP-запросов.

Факты за **ноябрь и декабрь 2025 отсутствуют и не будут предоставлены**. Финальная модель должна предсказать всю сетку этих двух месяцев по истории января–октября. Внешний клиент передаёт только `route/date/hour`; дополнительные признаки для будущего формирует pipeline из календаря и разрешённой истории. Нельзя требовать у клиента `prediction`, будущие boardings, лаги из ноября–декабря или ground truth.

Поставка включает реально рассчитанные моделью 14 640 значений для публикации в PostgreSQL. `test_submission.csv` допустим как шаблон ключей, но его примерные predictions не заменяют работу модели. Внешний API извлекает по переданным ключам этот прогноз, а произвольный период дашборда — подмножество того же run. Онлайн-inference не требуется для такого сценария; одного кода чтения чужого готового CSV без воспроизводимого собственного forecast недостаточно для сдачи.

Дополнительно pipeline поддерживает выпуск на следующий календарный день (24 часа на маршрут) и произвольный заявленный среднесрочный диапазон 2–62 дня. Конкурсный прогноз на 61 день — обязательная поставка, а не замена отдельной проверки DAY. YEAR на 365/366 дней — опциональный сценарий после MVP. Горизонт выпуска и DAY/MONTH-агрегации интерфейса различаются: просмотр суток не запускает новую модель.

Из notebook можно перенести организацию сравнения моделей и календарные признаки после адаптации. Нельзя переносить его метрики как результат соревнования. В текущем notebook признаки строятся до split, средние для заполнения вычисляются на всём наборе, а лаги теста могут использовать реальные значения тестового периода. Для двухмесячного прогноза это требует переписывания логики без утечки. `shift(n)` по строкам не гарантирует календарный лаг n дней/часов.

TFT/GNN, остановочные графы и сторонние погодные признаки не обязательны. Реализовать Seasonal Naive, weighted weekly profile, Direct CatBoost, иерархический Daily TS × HourShare и сравнение с ансамблем. CatBoost становится явной зависимостью ML. Это обязательный набор проверяемых подходов, а не обещание, что самый сложный или ансамбль обязательно победит. LightGBM и дополнительные нейросети не требуются для приёмки.

## 4. Подготовка target и контроль качества

### 4.1. Агрегаты labels

1. Читать `;`, UTF-8/UTF-8 BOM, четыре ожидаемые колонки.
2. Явно разбирать train как ISO, test как `%d.%m.%Y`; при других источниках формат должен задаваться конфигурацией. В промежуточных и итоговых файлах использовать ISO.
3. Проверить целочисленные route/hour/boardings, неотрицательный конечный target, диапазон часов, уникальность ключа и допустимые маршруты.
4. Объединить историю по реальным датам, ограничить её `2025-01-01 … 2025-10-31`. Дубликаты с конфликтующими значениями не суммировать молча; останавливать подготовку с отчётом.
5. Создать полную календарную часовую сетку каждого конкурсного маршрута. Сохранить признак исходной наблюдаемости и происхождение заполненного значения.

### 4.2. Нули, пропуски и маршрут 5

Разделять «нет успешных валидаций при подтверждённом покрытии источника» и «неизвестно, были ли данные». В первом случае target равен нулю; во втором он остаётся missing с маской и не используется как достоверный факт без обоснования.

В отчёте подготовки зафиксировать правило организаторских агрегатов и результаты сверки с raw: обычные дни, ночные часы, границы файлов/месяцев и отдельно маршрут 5. Сверка выполняется потоковым чтением нужных колонок; для маршрута 5 проверить оба исходных файла, а не только небольшой сэмпл. Если обнаружены события №5, агрегировать их по общей формуле и выяснить расхождение с labels.

Для первого baseline допускается явная исследовательская гипотеза: отсутствующая строка агрегата означает ноль. Она должна быть помечена в отчёте; до аудита такие восстановленные данные нельзя выдавать backend за подтверждённую полную историю для нормализации.

Для маршрута без истории выбрать и зафиксировать fallback: нулевой прогноз, если отсутствие событий подтверждено; иначе общий профиль по часу/типу дня с отдельно описанным способом задания масштаба. Нельзя без объяснения копировать поток другого маршрута. Сравнить доступные варианты на имитации недостатка истории у известных маршрутов. При неопределённости явно описать её в отчёте. В любом случае №5 обязан иметь 1 464 прогнозные строки.

### 4.3. Сырые события

При восстановлении агрегатов:

- Успешная посадка определяется `validation_result == 1`; дополнительные фильтры по `tran_type_id` без обоснования не вводить.
- Номер брать из `ngpt_route`, например `25 трамвай → 25`, с отчётом о нераспознанных значениях.
- Час и дату брать из `tran_date_time`, не из `input_date_time`, `begin_date_time` или имени файла.
- Учитывать суточные хвосты файлов; разбиение выполнять после разбора timestamp. Не терять события на границе месяцев и не включать факты после cutoff.
- Проверить повторы между файлами. Полные дубли событий и конфликтующие записи различать; не считать `tran_no` глобально уникальным без проверки.
- `place_id` — депо/площадка, а `pass_route` — зашумлённая цепочка пересадок. Они не дают достоверных `stop_id` или номера маршрута.
- Обрабатывать файлы порциями с `usecols`/явными типами и агрегировать частичные счётчики. Не требовать загрузки 10,4 ГБ CSV в RAM.

Промежуточный отчёт содержит диапазоны дат, число строк и событий до/после фильтрации, отказы парсинга, дубли, покрытия route-hour, распределение нулей и пропусков. Сырые карточные/транзакционные идентификаторы не нужны в итоговом датасете модели и веб-артефактах.

## 5. Валидация без утечки

Схема локальной проверки и финального обучения:

| Стадия | Доступная для обучения история | Период прогноза |
|---|---|---|
| Локальная оценка | 01.01–31.08.2025 | 01.09–31.10.2025, 61 день одним горизонтом |
| Финальное обучение | 01.01–31.10.2025 | 01.11–31.12.2025, 61 день одним горизонтом |

`test.csv`/`labels_day_test.csv` содержит доступные исторические факты, поэтому после выбора подхода его можно включить в финальное обучение. Реальные ноябрь–декабрь недоступны. `test_submission.csv` нельзя использовать как target.

Использовать expanding-window folds: январь–апрель → май–июнь (61 день), январь–июнь → июль–август (62 дня), январь–август → сентябрь–октябрь (61 день). Параметры, окна профилей и веса ансамбля подбирать на первых двух folds; третий оставлять итоговым holdout. Если его результаты использованы для дальнейшего подбора, пометить `evaluation_role=tuning` и не называть независимой оценкой. Random split запрещён. Отдельно дать разрез качества первых 30 дней и полного горизонта.

Для DAY добавить rolling-origin backtest на следующий календарный день: на каждом origin разрешены только факты до конца предыдущего дня. Частоту переобучения/обновления профилей зафиксировать в config и воспроизвести в финальном predict. Реальные вчерашние факты допустимы для нового DAY-origin, но недопустимы для продолжения ранее выпущенного MONTH-run. Сравнить DAY и среднесрочный подход на общей доступной 24-часовой сетке, не смешивать эти метрики в одну.

Каждый fold должен имитировать прогноз сразу на весь горизонт:

- Признаки обучаются и статистики вычисляются только до cutoff соответствующего fold.
- Реальные значения сентября–октября не подмешиваются в лаги/rolling для следующих дат этого же двухмесячного прогноза.
- Для горизонта дальше последнего известного лага использовать либо рекурсивные прогнозы, либо прямую модель по известным календарным признакам, либо многогоризонтную постановку. Выбранный способ описать и одинаково применять при backtest и финальном predict.
- Календарные лаги строить по полной часовой сетке в пределах маршрута, со сдвигом перед rolling.
- Заполнение пропусков, масштабирование и кодирование категорий обучаются только на train fold.
- Фактическую будущую погоду, будущие наряды и snapshot справочника 2026 года нельзя выдавать за доступные на cutoff признаки.

## 6. Модели и признаки

### 6.1. Seasonal Naive и weekly profile

Seasonal Naive: `prediction(t)=y(t−168h)`, только если исходный час известен на cutoff. Для прогноза дальше недели повторять последнюю доступную недельную сезонность: рекурсивно использовать собственный прогноз либо эквивалентно отступать на целое число недель к последнему известному соответствующему часу. Нельзя прочитать реальный `t−168h`, если он оказался внутри validation/future. Пропущенное значение обрабатывать через заранее заданный fallback, а не подставлять будущий факт.

Weighted weekly profile: профиль `(route, day_of_week, hour)` по последним четырём завершённым неделям до origin, с неотрицательными весами суммой 1. Веса `0.4/0.3/0.2/0.1` — стартовая гипотеза, подбор только на tuning folds. Для 61-дневного run профиль фиксируется на origin; при неполной истории перенормировать доступные веса и применять fallback `(route,hour)`, затем стратегию маршрута 5 из раздела 4. Дополнительно сравнить средний/медианный профиль за 4/8 недель.

### 6.2. Direct CatBoost

Глобальная модель для всех маршрутов; одна целевая точка — `route × timestamp`. `route` — категориальный признак. Обязательные календарные признаки: час, день недели/месяца/года, неделя года, месяц, выходной, линейное время от начала истории, циклические hour/dow. Праздник/предпраздничный день и перенесённый рабочий день строятся по сохранённому календарю с версией источника, а не угадываются по номеру дня недели.

Исторические признаки: route-hour и route-dow-hour mean/median, recent 4w/8w profile, recent level, trend. Все они должны быть доступны на origin. При обучении строки с target-derived профилями готовятся для исторических origins: профиль строится только по наблюдениям до этого origin, target — после него. Нельзя вычислить среднее по всему train и присоединить его к тем же обучающим target без временного ограничения. Для историй малой длины первые origins отбрасываются или используют описанный fallback.

Direct MONTH использует известный будущий календарь, профили, замороженные на origin, и при необходимости `horizon_step`. Короткие target-relative `lag_24/48/168/336`, rolling/EMA допустимы лишь в эксперименте с явно воспроизведённой рекурсией или привязкой к origin. Название «direct» не разрешает читать неизвестный лаг из будущего. У DAY `lag_1/lag_2` относительно второго и последующих прогнозируемых часов тоже неизвестны; применять те же правила.

### 6.3. Daily Time Series × HourShare

1. Из подтверждённой полной сетки получить `DailyTotal(route,date)=sum(boardings за 24 часа)`. Неполный наблюдаемый день не считать полным total.
2. Предсказать дневные totals с учётом недельной сезонности и тренда. Реализовать как минимум суточный CatBoost и один статистический кандидат (ETS/Holt–Winters либо STL + модель тренда); SARIMA — дополнительный эксперимент.
3. На истории до origin оценить доли `HourShare(route,day_of_week,hour)`. Например, сумма посадок каждого часа, делённая на сумму посадок всех часов для того же route/dow в окне. Доли неотрицательны и суммируются в 1 для 24 часов.
4. Восстановить `HourlyPrediction = max(0, DailyForecast) × HourShare`. Профиль фиксируется до конца данного выпуска; допустимость изменения по будущему календарю должна быть обучена на прошлом.

Если профиль route/dow имеет нулевой знаменатель, использовать профиль route по всем дням; при его отсутствии — подтверждённые эксплуатационные часы, а если и их нет, явный равномерный fallback `1/24`. Такой fallback маркировать; при подтверждённом нулевом DailyTotal все прогнозы всё равно нулевые. Не выдавать равномерность за знание расписания.

В непрерывном выходе сумма 24 часов должна совпадать с DailyForecast с численной точностью. Внутри этой компоненты, если требуется целочисленное распределение заданного дневного total, применять метод наибольших остатков с детерминированным порядком часов. Для финального ансамбля смешивать непрерывные компоненты и лишь затем применять общее округление submission; сумма итогового ансамбля не обязана равняться total отдельной Daily TS-модели. Отчёт оценивает окончательные почасовые результаты, а не только дневные totals.

STL исследовать на train-истории для тренда/сезонности; двустороннее сглаживание полного train+validation ряда запрещено. Суточная модель помогает получить почасовой MONTH-прогноз; API затем суммирует готовые часы для графика, не вызывает Daily TS повторно.

### 6.4. Ансамбль и выбор финальной модели

```text
prediction = w1 * DirectCatBoost + w2 * DailyTSHourly + w3 * Seasonal
w_i >= 0; sum(w_i) = 1
```

Подбор весов — по объединённым предсказаниям tuning folds, с глобальным WAPE по суммам. Обязательны сравнение компонентов и ансамбля, сохранение весов, ablation-таблица и оценка на holdout. Веса могут быть нулевыми; если ансамбль не улучшает устойчиво лучшую компоненту, поставить её и описать результат. Не усложнять модель ради формального наличия ансамбля. Веса по маршрутам допустимы только после достаточной отдельной проверки, иначе один набор весов на класс горизонта.

### 6.5. YEAR и внешние факторы

YEAR — отдельный `forecast_kind=scenario` с почасовой сеткой на 365/366 дней. Использовать тренд, известный календарь и недельно-часовой профиль; месячные коэффициенты без полного годового цикла считаются сценарными предположениями. Сохранять `scenario_assumptions`, ограничения и источник коэффициентов. Не заявлять подтверждённую годовую точность по 10 месяцам истории. Отсутствие YEAR не блокирует сдачу.

Предусмотреть простой интерфейс `get_features(keys, as_of)` для `CalendarProvider` (обязателен) и будущих Weather/Traffic/Event providers. Для optional providers без источников не создавать фиктивные значения и не требовать их запуска. Сохранять происхождение и время доступности внешнего значения. Фактическая будущая погода не является future-known feature; допустим только архив прогноза, известного на соответствующий origin.

## 7. Метрики и выбор решения

Основная метрика организаторов:

```text
WAPE = sum(abs(y - prediction)) / sum(y)
WAPE_score = max(0, 1 - WAPE)
```

Сначала соединить факт и прогноз по полному ключу `(route,date,hour)`, проверить уникальность и совпадение сетки. Метрику считать по всем подтверждённым значениям оценки, включая восстановленные подтверждённые нули. Если часть фактов неизвестна, явно указать покрытие и не называть результат полной конкурсной метрикой.

Считать глобальный WAPE по суммам, а не среднее WAPE маршрутов. Дополнительно предоставить WAPE/MAE/RMSE по маршрутам, каждому часу, месяцам, длине горизонта и пиковым часам. Пики определить до оценки (фиксированным списком часов либо по train-профилю) и сохранить в config. Для среза с `sum(y)=0` WAPE/score пометить как undefined/null с причиной, дополнительно показать MAE и число ложных положительных прогнозов; не допускать деления на ноль и не придумывать официальное правило организаторов.

Все сравниваемые модели используют одинаковые folds, ключи оценки и постобработку. Оценить именно сохраняемые прогнозы после отсечения отрицательных значений и согласованного округления; при необходимости отдельно привести метрику непрерывного выхода.

Из README организаторов: пример submission имеет скрытый score около 0,48. Это ориентир источника, не измеренный результат текущего репозитория и не доказательство качества на локальном holdout. Цель — улучшить локальный baseline; численное качество на скрытом ноябре–декабре можно утверждать только после проверки организаторами.

Сохранять машиночитаемый `metrics.json` в формате `Evaluation` из Backend §8.3: `evaluation_id`, model/config hash, checksum данных, folds/cutoffs, роль tuning/holdout, горизонт, sample_count, actual_sum, coverage и срезы. `coverage` — доля подтверждённых целевых ключей относительно ожидаемой сетки среза. В JSON не допускаются NaN/Infinity. Backend импортирует этот отчёт отдельно и показывает качество исторической проверки, а не недоступного будущего.

## 8. Реализация и интерфейс команд

Реализовать модули в `ml/src/`:

| Модуль | Ответственность |
|---|---|
| `preprocessing.py` | Чтение/проверка labels и raw, восстановление сетки, отчёт качества |
| `features.py` | Признаки с явным cutoff и одинаковой логикой train/predict |
| `baselines.py` | Seasonal Naive и weighted weekly profiles с корректным длинным горизонтом |
| `timeseries.py` | Суточные статистические кандидаты и train-only decomposition |
| `hierarchical.py` | DailyTotal, HourShare, реконструкция и сохранение сумм |
| `train.py` | Baseline, кандидаты, временные folds, обучение, сохранение |
| `evaluate.py` | Единственная реализация WAPE, сверка ключей, отчёты |
| `predict.py` | Загрузка артефакта, прогноз на весь диапазон, submission |
| `geolinking.py` | Контракт сопоставления события с географией, статусы и причины отсутствия |
| `providers.py` | CalendarProvider и протокол для будущих внешних факторов |

Предлагаемый обязательный CLI из корня проекта; аргументы должны быть реализованы и описаны:

```text
python -m ml.src.preprocessing --source labels --data-dir data/raw --output-dir data/processed
python -m ml.src.preprocessing --source raw --data-dir data/raw --output-dir data/processed/raw_audit
python -m ml.src.train --data-dir data/processed --train-end 2025-08-31 --valid-start 2025-09-01 --valid-end 2025-10-31 --output-dir ml/models/validation
python -m ml.src.evaluate --actual data/processed/actual_hourly.csv --prediction ml/models/validation/predictions.csv --from 2025-09-01 --to 2025-10-31
python -m ml.src.train --data-dir data/processed --train-end 2025-10-31 --output-dir ml/models/final
python -m ml.src.predict --model-dir ml/models/final --profile competition --from 2025-11-01 --to 2025-12-31 --output data/processed/submission.csv
python -m ml.src.predict --model-dir ml/models/final --profile standard --horizon day --from 2025-11-01 --to 2025-11-01 --output data/processed/day_forecast.csv
```

Поддержать запуск без notebook. Конфигурацию выбранной модели/признаков/seed хранить в версионируемом файле; путь передавать CLI. Финальный train использует выбранную конфигурацию и не делает подбор по ноябрю–декабрю. Внешний каталог датасета допускается вместо `data/raw`.

Артефакт модели содержит поддерживаемые горизонты; пример DAY использует общий артефакт, только если он поддерживает day. Для отдельной DAY-модели явно передать её каталог. Несовместимый `--horizon` завершается ошибкой, не подменяется иной моделью. Добавить `--config` с настройками folds/моделей, `--backtest` для всех временных folds; приведённые команды отдельного train/valid остаются удобным запуском одного fold. `predict` не требует PostgreSQL: интеграция с ним выполняется CLI backend.

CSV достаточно для малого итогового датасета. Если используются Parquet, явно добавить движок чтения/записи в зависимости: текущий `requirements.txt` его не содержит. Описанный старым README `ml/requirements.txt` пока отсутствует; создать его для дополнительных ML-зависимостей и указать порядок установки относительно корневого файла без конфликтующих версий.

JSON metadata рядом с submission и metrics.json обязательны для полной воспроизводимой ML-поставки, но backend технически принимает корректный day/month CSV отдельно без них. YEAR требует описания сценария. Метрики не добавлять колонками в submission. `relative_load`, индексы и цвета не являются выходами ML. Восстановленные предположительные нули сохранять как missing для истории backend до подтверждения; исследовательский датасет может иметь отдельно заполненные по гипотезе значения с явным статусом.

### Геопривязка как отдельный модуль

`geolinking.py` принимает route, timestamp, доступные garage_number/bus_exit_no и snapshot расписания. Возвращает route, timestamp, `stop_id|null`, `segment_id|null`, `geolink_status=exact|schedule_match|approximate|unavailable`, `geolink_confidence` (0–1 либо null), `reason`, `reference_version`. При наличии segment_id использовать ту же схему идентификаторов, что в справочном API, через документированный алгоритм/общий небольшой модуль; ML не импортирует FastAPI-приложение.

Для текущих событий 2025 года и расписания/нарядов 2026 года нормальный результат — unavailable, nullable ID и confidence=null. Не брать «ближайшую остановку» только по времени без действующего расписания. `exact` допускается только при прямом надёжном источнике привязки; `schedule_match` и `approximate` требуют версии алгоритма и описанного способа оценки confidence. При неоднозначности без обоснованного выбора — unavailable.

MVP включает интерфейс, реализацию unavailable и тесты ограничений источников. Реальный matcher — расширение после появления покрытия по датам, маршрутам и транспортным средствам. Геопривязка не меняет суммы route-hour target, не создаёт обязательный stop-level forecast и не добавляет колонки в submission.

Тяжёлые модели и данные остаются вне Git согласно существующему `.gitignore`. В Git — код, конфигурация, небольшой обезличенный/синтетический fixture, тесты и текстовый отчёт. При передаче модели отдельно указать её checksum и способ получить/воспроизвести артефакт.

## 10. Критерии приёмки

- Pipeline запускается из CLI без ручного выполнения notebook и без сетевого скачивания стороннего датасета.
- Различающиеся форматы дат labels разобраны правильно; target соответствует успешным посадкам.
- Есть отчёт по разреженности и отдельное решение для маршрута 5; неизвестное не скрывается под видом подтверждённого нуля.
- Временная проверка воспроизводит 61-дневный прогноз без использования фактов после cutoff в признаках. Изменение целевых значений validation не меняет признаки/предсказания при фиксированной обученной модели.
- Seasonal Naive, weighted profile, Direct CatBoost, Daily TS и ансамбль сравнены одинаковым способом; есть статистический суточный кандидат, отчёт о выборе компонентов/весов и измеренные ресурсы, без обещаний скрытого score.
- Проверен отдельный 24-часовой backtest и горизонты 30–62 дня; веса не подобраны на итоговом holdout. Короткие лаги не получают фактического будущего даже в DAY.
- Финальный pipeline использует доступную историю до 31.10.2025 включительно и формирует точную сетку всех десяти маршрутов на ноябрь–декабрь.
- Автоматическая проверка submission контролирует состав/порядок колонок, типы, ключи, диапазоны, количество, отсутствие NaN/Infinity/отрицательных значений.
- Тесты проверяют parser raw, target, обе схемы дат, полную сетку, сезонное повторение дальше недели, train-only профили, WAPE/нулевой знаменатель, неотрицательность, HourShare sum=1 и сохранение DailyTotal при реконструкции.
- Geolinking возвращает unavailable при неподходящих датах/источниках, не изменяет target; CalendarProvider воспроизводим. Optional YEAR всегда маркирован scenario и содержит предположения.
- Backend импортирует результат без ручной правки и без загрузки ML-модели; UI показывает те же значения.
- Вызов POST только с route/date/hour возвращает предсказания поставленной модели. Полная сетка, произвольная несмежная выборка и период 15.11–05.12 совпадают с артефактом этого run. Ни обучение, ни inference не используют факты после 31.10.2025 для конкурсного выпуска.
