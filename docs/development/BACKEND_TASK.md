# Отложенная задача backend — DEV-01

Статус: **отложена, не выполнена**. Обновлено: 26.09.2026. FE-01 завершена, приоритет переключён на frontend FE-02; текущая карточка находится в [ACTIVE_TASK.md](ACTIVE_TASK.md).

Карточка сохранена для дальнейшей backend-разработки. Она не является зависимостью создания frontend на явно тестовых данных, но нужна перед изменением работающего backend.

## Цель

Зафиксировать существующее поведение справочного FastAPI регрессионными тестами, чтобы последующее добавление PostgreSQL и прогнозов не сломало рабочие URL.

## Основание и входы

- [Текущая архитектура](ARCHITECTURE.md).
- [Backend-ТЗ, проверки](../spec/BACKEND.md#11-проверки-и-поставка).
- [main.py](../../web-forecast/app/main.py), модули [api](../../web-forecast/app/api/), [GTFSRepository](../../web-forecast/app/repositories/gtfs_repository.py).
- Реальный справочник: `dataset/spravochniki/Хакатон_справочники_трамвай_10_маршрутов.xlsx`.

Зависимости: установлен Python и зависимости существующего backend; нужны явно описанные тестовые зависимости. БД, frontend и ML для этой задачи не требуются.

## Ожидаемый результат

Из корня проекта запускается воспроизводимый набор pytest-тестов существующих endpoint. Тесты проверяют HTTP-статусы, формы ответов и реальные фильтры, а не только факт вызова функции.

Проверить `/`, `/health`, `/api/routes`, поиск маршрута по номеру и GTFS ID, `/api/stops`, поиск остановки и оба endpoint нарядов. Отсутствие старой прогнозной заглушки среди подключённых роутеров описать как исходное состояние; не создавать постоянный тест, запрещающий будущий прогнозный API.

## Планируемые изменения

- `web-forecast/tests/` — тесты и fixtures.
- `requirements-dev.txt` — новые тестовые зависимости с совместимыми закреплёнными версиями.
- При необходимости минимальный pytest config для импорта `app` из `web-forecast/`.
- TESTING.md, CHANGELOG_AGENT.md и эта карточка — команды, результаты и статус.

Это границы предполагаемой задачи, а не запрет необходимого исправления. Если обнаружен дефект production-кода, опиши его и минимальное изменение отдельно; не превращай тестовую задачу в переписывание backend.

## Не входит

PostgreSQL, миграции, конфигурационный рефакторинг, прогнозные endpoint, ML, frontend, изменение XLSX и вложенного проекта. Не менять существующие ответы ради удобства тестов.

## Критерии приёмки

- [ ] `/` и `/health` возвращают существующие поля и HTTP 200.
- [ ] Списки маршрутов/остановок возвращают `count`, согласованный с длиной массива.
- [ ] Маршрут с коротким номером 1 находится; поиск по полученному GTFS ID даёт ту же запись.
- [ ] Неизвестный GTFS ID/номер/stop_id возвращает 404 существующего справочного API.
- [ ] Остановка, взятая из справочного списка, доступна по её ID.
- [ ] Фильтрация нарядов по route_id/date возвращает только подходящие записи; пустая выборка — 200 и пустой массив.
- [ ] Формы `{count, filters, assignments}` и `{route_id, date, count, vehicles}` сохранены.
- [ ] JSON не содержит NaN; незаполненные поля корректно сериализуются.
- [ ] Тесты не обращаются к сети, внешней БД и большому raw-датасету.
- [ ] Тестовая команда, зависимости, результаты и ограничения записаны в TESTING и журнале.

404 выше относится к существующему справочному API. Для будущего `POST /api/predict` неподдерживаемый конкурсный номер — **422**, как указано в ТЗ.

## Проверка результата

После создания тестов и установки их зависимостей:

```powershell
python -m pytest web-forecast/tests -q
git diff --check
git diff --stat
git status --short
```

Сейчас первая команда не является готовой проверкой: каталог тестов и dev requirements пока отсутствуют. Не записывать «все тесты пройдены» до фактического запуска.

## Прогресс / передача работы

- Сделано: подготовлена карточка на основании текущего кода и ТЗ.
- Не сделано: реализация тестов, установка тестовых зависимостей, их запуск.
- Следующий шаг после запуска задачи: изучить фабрики роутеров и загрузку Excel; выбрать fixtures, сохраняющие проверку настоящей фильтрации.
- Последний результат проверок: тесты этой задачи не запускались.

Для новой карточки сохрани структуру: ID/статус → цель → источники/зависимости → ожидаемый результат → границы → критерии → команды → прогресс. Итог закрытой задачи сначала перенеси в CHANGELOG_AGENT.
