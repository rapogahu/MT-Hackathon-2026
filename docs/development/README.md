# Как вести разработку MTTECH с этим комплектом

Комплект подготовлен 26.09.2026 по ТЗ 4.2 и существующему коду. Все новые рабочие памятки находятся в этой папке; полное ТЗ и описание реализации остаются на прежних местах.

## 1. Что здесь лежит

| Файл | Для чего нужен | Когда обновлять |
|---|---|---|
| [AGENTS.md](AGENTS.md) | Короткие правила работы агента | При изменении постоянных договорённостей |
| [ACTIVE_TASK.md](ACTIVE_TASK.md) | Одна текущая задача: результат, границы, критерии, прогресс | Перед новой задачей и по её завершении |
| [ARCHITECTURE.md](ARCHITECTURE.md) | Краткая карта того, что действительно существует | После изменения реализации |
| [SPEC.md](SPEC.md) | Короткая памятка ключевых контрактов и ссылки на ТЗ | После изменения требований |
| [DECISIONS.md](DECISIONS.md) | Почему выбраны архитектура и контракты | При принятии или пересмотре решения |
| [TESTING.md](TESTING.md) | Команды проверок с указанием их текущей доступности | Когда появляется/меняется проверка |
| [CHANGELOG_AGENT.md](CHANGELOG_AGENT.md) | Что сделано и чем проверено | После каждой законченной задачи/передачи работы |
| [TASKS.md](TASKS.md) | Предлагаемый порядок небольших задач | Когда меняются зависимости и приоритеты |

Полные источники: [реализованная архитектура](../CURRENT_ARCHITECTURE.md), [общий контракт](../spec/README.md), [Backend](../spec/BACKEND.md), [Frontend](../spec/FRONTEND.md), [ML](../spec/ML.md). Краткие файлы не заменяют точные схемы API.

## 2. Что постоянно держать в контексте

Минимальный постоянный набор на задачу: **AGENTS.md + ACTIVE_TASK.md + SPEC.md**. Это наша рекомендация организации работы, а не требование инструмента. Не нужно прикреплять все документы в каждом сообщении одного и того же диалога.

| Ситуация | Что добавить к постоянному набору |
|---|---|
| Новый диалог / возвращение после перерыва | ARCHITECTURE.md и последнюю относящуюся к задаче запись CHANGELOG_AGENT |
| Backend / внешний POST | Нужные разделы `docs/spec/BACKEND.md`, особенно §8.5, и изменяемые модули |
| SQL / импорт | Backend §6–7, соответствующие ADR, модели БД/миграции после их появления |
| Frontend | Frontend-ТЗ и только используемые DTO из Backend §8 |
| ML | ML-ТЗ, контракт результата, код нужной стадии и отчёт данных; не сырые гигабайты CSV |
| Изменение архитектуры | DECISIONS.md, CURRENT_ARCHITECTURE.md и соответствующие разделы полного ТЗ |
| Проверка/исправление ошибки | TESTING.md, точная ошибка, воспроизведение и затронутый тест/код |

Не добавляй постоянно весь CHANGELOG, все notebooks, старые версии ТЗ, вложенный проект и большие данные. Укажи путь и попроси прочитать нужный раздел. Ссылки помогают найти документ, но не гарантируют, что всё его содержимое уже прочитано: в начале новой задачи явно перечисляй необходимые источники.

## 3. Как подключить AGENTS.md

Сейчас файл расположен в `docs/development/AGENTS.md`. При работе из корня он **не становится автоматически правилом всего репозитория**. Обнаружение проектных инструкций идёт от корня к текущему рабочему каталогу; для общего действия нужен корневой файл, а для инструкции в отдельной папке можно явно попросить её прочитать. Это поведение описано в [официальной документации OpenAI](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

В этом комплекте выбран вариант «все файлы в отдельной папке». Начинай задачу из корня `MTTECH/` таким сообщением:

```text
Прочитай и используй правила docs/development/AGENTS.md.
Прочитай docs/development/ACTIVE_TASK.md и docs/development/SPEC.md.
Выполни только задачу из ACTIVE_TASK, сверив релевантный код и разделы ТЗ.
Кратко сообщи план и файлы, затем реализуй, проверь и обнови журнал.
```

Если позже нужен автоматический вход, создай в **корне** `MTTECH/AGENTS.md` короткую ссылочную инструкцию, сохранив основной текст в этой папке:

```markdown
# MTTECH
Перед работой прочитай и применяй docs/development/AGENTS.md.
Текущая задача — docs/development/ACTIVE_TASK.md; выполняй её по запросу пользователя.
Краткий контракт — docs/development/SPEC.md.
```

Это инструкция агенту прочитать документ, не специальный механизм include. Корневой файл сейчас не создан. После его добавления начни новую сессию и попроси перечислить реально прочитанные источники инструкций: цепочка инструкций строится при запуске. [Правила обнаружения и проверки](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

Не копируй правила проекта в глобальный `~/.codex/AGENTS.md`: они относятся к MTTECH. Рабочий каталог остаётся корнем проекта, а не вложенным `MT-Hackathon-2026/`.

## 4. Цикл одной задачи

1. Выбери небольшой пункт из TASKS. Проверь, выполнены ли зависимости.
2. Заполни ACTIVE_TASK: один проверяемый результат, входы, ожидаемые изменения, критерии и команды.
3. Дай агенту сообщение выше. План нужен для понимания работы; он не вводит обязательную паузу на подтверждение каждого изменения.
4. По завершении прочитай отчёт и новую запись CHANGELOG_AGENT. Смотри фактически запущенные проверки, а не обещание «должно работать».
5. Сам повтори короткий сценарий приёмки из TESTING/карточки. Если что-то не работает, приложи команду, результат и точную ошибку.
6. Старый результат сохрани в журнале, затем замени содержимое ACTIVE_TASK новой задачей. Не превращай карточку в список из десятков параллельных поручений.

Подготовленная здесь первая задача **DEV-01 — регрессионные тесты текущего backend** ещё не запущена. Она не подключает PostgreSQL и не реализует POST. В данный запрос входило создание рабочего комплекта, а не выполнение следующей задачи.

## 5. Формулировки запросов

Продолжение после перерыва:

```text
Прочитай правила, ACTIVE_TASK и последнюю запись CHANGELOG_AGENT
в docs/development/. Сверь их с текущим git status и кодом.
Продолжи незавершённые пункты этой задачи, не повторяя уже сделанное.
```

Разбор ошибки:

```text
В рамках текущей ACTIVE_TASK исправь воспроизведение:
команда: <точная команда>
ожидание: <что должно произойти>
получено: <ответ или traceback>
Сначала найди причину, затем внеси минимальное исправление и проверь сценарий.
```

Изменение требования:

```text
Новое требование: <описание>.
Сверь его с docs/spec/ и docs/development/DECISIONS.md.
Обнови затронутые контракты и карточку задачи, затем выполни разрешённую реализацию.
```

## 6. Как не дать документам разойтись

- ACTIVE_TASK меняется часто; AGENTS — редко.
- Утверждение «уже работает» добавляется в ARCHITECTURE только после реализации и проверки.
- При изменении API сначала согласуй полный контракт Backend/Frontend/ML, затем обнови короткий SPEC и соответствующий ADR в том же изменении.
- В DECISIONS не переписывай прошлое молча: пометь старое решение заменённым и укажи новое.
- В CHANGELOG записывай проверенные команды, ограничения и продолжение. Не копируй туда весь diff или вывод обучения.
- Если документация устарела относительно кода, укажи расхождение. Код — свидетельство реализации, но не разрешение менять смысл ТЗ без объяснения.
