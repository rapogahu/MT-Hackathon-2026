# Правила разработки MTTECH

Все пути ниже указаны относительно корня `MTTECH/`. Основа — ТЗ 4.2.

## Источники

- Текущая реализация: `docs/CURRENT_ARCHITECTURE.md`; кратко — `docs/development/ARCHITECTURE.md`.
- Требования: `docs/spec/README.md` и профильные BACKEND/FRONTEND/ML; кратко — `docs/development/SPEC.md`.
- Решения: `docs/development/DECISIONS.md`.
- Текущая задача: `docs/development/ACTIVE_TASK.md`.
- Проверки и журнал: `docs/development/TESTING.md`, `docs/development/CHANGELOG_AGENT.md`.

Код показывает, что реализовано; ТЗ — что нужно реализовать. Не выдавай требования за существующие возможности. При расхождении кратких памяток с полным ТЗ сверяй исходный раздел и исправляй памятку. Новые указания пользователя учитывай прежде прежних проектных договорённостей; необходимое изменение контракта отражай в документах.

## Основные правила

1. Работай в основном `MTTECH/`; не изменяй вложенный `MT-Hackathon-2026/` в рамках обычных задач.
2. Сохраняй `web-forecast/app/main.py`, фабрики роутеров, `GTFSRepository` и рабочие routes/stops/assignments API. Меняй их только в объёме задачи.
3. Целевая архитектура: справочник Excel в памяти; PostgreSQL для истории, прогнозов, нормализации и метрик. Сервисный слой добавляется поверх текущего кода.
4. Внешний POST принимает `route/date/hour`, возвращает те же строки с `prediction`. Внутренний CSV имеет `route;date;hour;prediction`. Не смешивай эти интерфейсы.
5. `prediction` — число посадок за час на всём маршруте, не уникальные люди и не заполненность вагона.
6. Конкурсный прогноз: 01.11–31.12.2025, 10 маршрутов, 14 640 часов-маршрутов. Фактов ноября–декабря нет; история ограничена 31.10.2025.
7. Не создавай фиктивные stop-level прогнозы, геометрию, realtime или метрики качества. Не используй будущее в признаках/backtest.
8. Не путай короткий номер маршрута с GTFS ID. `trip_short_name=0` не является уникальным ключом пути.
9. ML выполняется пакетно. HTTP получает готовые значения одного run; не обучает и не запускает полный inference на каждый запрос.
10. Не добавляй микросервисы, очереди, Redis, PostGIS и альтернативный backend без конкретной потребности задачи. PostgreSQL, Alembic, CatBoost и React уже предусмотрены ТЗ.
11. Сохраняй пользовательские изменения; не откатывай чужой diff. Не коммить сырые данные, модели, секреты и локальные абсолютные пути.

## При работе над frontend

Работай в корневом `frontend/` по текущей FE-карточке и `docs/spec/FRONTEND.md`; DTO сверяй с Backend §8. Пока прогнозный API отсутствует, разрешён отдельный dev/test fixture-адаптер того же контракта с явной маркировкой. Ошибка HTTP не включает fixtures автоматически; production использует реальный API. Не реализуй backend/ML вместо поставленной UI-задачи. Приёмку на fixtures отличай от интеграционной приёмки продукта.

## Перед изменениями

1. Прочитай задачу, проверь её статус и зависимости. Подготовленная карточка сама по себе не запускает работу.
2. Посмотри `git status`, релевантный код и нужные разделы ТЗ; не читай весь датасет/историю чата без причины.
3. Кратко сообщи план и предполагаемые файлы. Продолжай разрешённую работу без отдельного подтверждения каждого шага.
4. Если обязательная зависимость не готова, опиши конкретный пробел; не подменяй её заглушкой, выдаваемой за production-реализацию.

## После изменений

1. Выполни проверки по области изменений из TESTING; запиши точные команды и фактические результаты. Не называй отсутствие тестов успешным прохождением.
2. Для frontend запускай build/typecheck, когда соответствующие команды реализованы; для SQL — интеграционные проверки на PostgreSQL.
3. Проверь `git diff --check`, `git diff --stat`, `git status --short`; новые неотслеживаемые файлы перечисли отдельно.
4. Добавь запись в CHANGELOG_AGENT и обнови статус/остаток ACTIVE_TASK. Архитектуру и ADR меняй только при соответствующих изменениях.
5. В отчёте укажи результат, проверки и оставшиеся ограничения. Не приписывай себе весь уже существовавший diff.

## Готовность

Задача завершена, когда выполнены её критерии, применимые проверки пройдены, совместимость проверена и документация соответствует результату. Непроверенное явно помечается. Для документальной задачи не требуется запускать обучение, создавать тесты продукта или собирать отсутствующий frontend.
