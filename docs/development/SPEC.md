# Краткий контракт продукта

Основа: [ТЗ 4.2](../spec/README.md). Здесь только обязательные ориентиры; точные схемы и крайние случаи находятся в профильных документах.

## Данные и смысл

- `prediction` — прогноз числа посадок за календарный час на всём маршруте; target — число успешных `validation_result == 1`.
- Маршруты: `1,5,7,11,12,17,25,26,28,50`.
- Прогноз: 01.11–31.12.2025, 61 день × 24 часа × 10 маршрутов = **14 640 строк**. Фактов этих месяцев нет; обучение и признаки ограничены историей до конца октября.
- Время продукта — Europe/Moscow. Нулевой прогноз — значение; отсутствие данных — отдельное состояние.

## Два разных интерфейса

| Интерфейс | Вход | Выход / смысл |
|---|---|---|
| Внешний `POST /api/predict` | JSON-массив `{route,date,hour}` | Массив `{route,date,hour,prediction}`, ровно четыре поля |
| Внутренний ML → импорт backend | CSV `route;date;hour;prediction`, UTF-8, ISO-даты | Публикация готового модельного run в PostgreSQL |

Для POST допустимы ISO и M/D/YYYY; **11/1/2025 = 1 ноября**. Ответ сохраняет принятую строку даты, порядок и повторы входных элементов. Неподдерживаемый route/неверные данные → 422; отсутствующий опубликованный прогноз → 503; неизвестный явный run_id → 404. Весь запрос валидируется атомарно. run_id передаётся необязательно в query, фактический UUID — в заголовке ответа. Лимит 1–14 640 строк и 2 MiB. [Полный внешний контракт](../spec/BACKEND.md#85-внешний-api-прогноза-по-списку-ключей).

## Дашборд

Маршрут/ALL, DAY/MONTH/PERIOD, произвольные включительные границы внутри ноября–декабря, «Получить прогноз», график, карта, KPI и CSV. 15.11–05.12 — 504 часа одного маршрута или 5 040 точек ALL. API, график и экспорт должны совпадать для одних ключей и run_id. Час карты остаётся отдельным снимком внутри диапазона. [Frontend](../spec/FRONTEND.md).

Географический выбор направления/остановки/участка не меняет route-level prediction. Геометрия доступна лишь для части конкурсных маршрутов; остальные сохраняют прогноз и экспорт. Схема из остановок не выдаётся за точную историческую трассу. YEAR — отдельный опциональный сценарный run, не экстраполяция в интерфейсе.

## Целевая архитектура и ML

Существующий FastAPI и справочные URL сохраняются. Excel остаётся в GTFSRepository в памяти; PostgreSQL хранит факты, runs, прогнозы, нормализацию, метрики. Новые ForecastService/MapService объединяют эти контуры; фронтенд — корневой `frontend/`. Alembic и Compose входят в целевую поставку. [Backend](../spec/BACKEND.md).

ML сравнивает Seasonal Naive, weighted weekly profile, Direct CatBoost, Daily TS × HourShare и ансамбль. Временные backtests имитируют настоящий горизонт, без фактов будущего; финальное решение выбирается по измеренному WAPE. Labels имеют разные форматы дат, не содержат №5 и явных нулей — нужен аудит, а не молчаливое заполнение. [ML](../spec/ML.md).

Относительную загрузку и индекс считает backend по Q05/Q95 маршрута при импорте. В обычном случае relative_load=0.5 даёт индекс 6; вырожденный fallback — 50% и индекс 5. Не пересчитывать шкалу на frontend или по текущему фильтру.

## Что считать готовностью

Реально полученный моделью конкурсный forecast → атомарный импорт → доступный POST и GET → период на дашборде → совпадающий экспорт, при сохранённых старых API и выполненных проверках. Чтение чужого готового CSV или константная заглушка не заменяют собственный ML-процесс.
