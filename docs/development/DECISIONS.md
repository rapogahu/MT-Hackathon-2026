# Решения проекта

Основа: [ТЗ 4.2](../spec/README.md), 26.09.2026. «Принято в ТЗ» означает целевое решение, а не готовую реализацию. Проверенный статус компонентов — в [ARCHITECTURE](ARCHITECTURE.md).

## ADR-001 — Развиваем текущий FastAPI

Статус: сохраняем существующую основу.

Решение: основной backend — `web-forecast/app/`, с текущей точкой входа, фабриками роутеров и `/api`. Существующие маршруты, остановки и наряды остаются совместимыми. Вложенный `MT-Hackathon-2026/` не является вторым сервисом.

Причина: справочный контур уже работает; перенос или переписывание увеличивает риск без продуктовой пользы. Следствие: сначала регрессионные тесты, затем добавление новых модулей.

## ADR-002 — Excel для справочников, PostgreSQL для прогнозов

Статус: принято в ТЗ; SQL-часть ещё не реализована. Заменяет предложение файлового хранилища прогнозов из ТЗ 3.0.

Решение: GTFSRepository продолжает читать небольшой Excel в память. PostgreSQL хранит actual batches, историю, прогнозные runs, значения, нормализацию и метрики. Alembic управляет схемой; PostGIS не нужен для построения линий между остановками.

Причина: сохранить рабочий код и одновременно получить атомарную публикацию, индексы и единый источник для workers. CSV — обменный ML-артефакт, не база данных HTTP-сервиса. [Backend §6](../spec/BACKEND.md#6-импорт-и-хранение-прогноза).

## ADR-003 — Target: посадки по маршруту и часу

Статус: принято по правилам датасета.

Решение: число успешных валидаций, route из `ngpt_route`, время из `tran_date_time`. Не считать уникальных людей и не трактовать поток как заполненность салона.

Причина: именно этот target измерим и оценивается в соревновании. Фактов ноября–декабря нет; 14 640 значений нужно предсказать по январю–октябрю. [ML §1](../spec/ML.md#1-цель).

## ADR-004 — Внешний запрос и внутренний прогноз различаются

Статус: принято по уточнению пользователя, ТЗ 4.2.

Решение: внешний `POST /api/predict` получает массив трёх полей route/date/hour, возвращает четыре поля с prediction. Внутренний импорт получает CSV уже с prediction. Клиент не поставляет модельные признаки или будущие факты.

Причина: API должен выдавать собственный прогноз системы. Минимальный внешний контракт не перегружается индексами и metadata; расширенные GET обслуживают дашборд. [Backend §8.5](../spec/BACKEND.md#85-внешний-api-прогноза-по-списку-ключей).

## ADR-005 — Однозначные даты и идентификаторы

Статус: принято в ТЗ; исправления ключей ещё предстоят.

Решение: canonical CSV/SQL/GET — ISO. POST дополнительно принимает M/D/YYYY и повторяет принятую строку даты в ответе; 11/1/2025 означает 1 ноября. Короткий route не равен GTFS route_id; trip_short_name не ключ. Геометрия использует конкретный путь и направление.

Причина: разные соглашения источников не должны незаметно менять дату или объединять маршруты. Формат даты нарядов YYYYMMDD сохраняется для совместимости справочного API.

## ADR-006 — Пакетный ML и неизменяемый run

Статус: принято в ТЗ.

Решение: ML заранее строит весь горизонт; API выбирает точки из PostgreSQL. Один запрос и все связанные блоки UI используют один run_id; новый импорт не меняет старый снимок. Смена периода не переобучает модель.

Причина: согласованность карты, графика, POST и CSV, воспроизводимость результатов, предсказуемая нагрузка. Отсутствующий forecast — 503, не нули и не пример submission.

## ADR-007 — Географическая навигация без фиктивной детализации

Статус: принято с учётом ограничений данных.

Решение: выбранные остановка/участок меняют выделение карты, но не forecast. Геометрия — справочная ломаная, с датами актуальности. Нет stop-level target — нет stop-level прогнозов. geolinking допускает unavailable.

Причина: нет полного исторического расписания и географии всех конкурсных маршрутов. Нельзя создавать ложную точность из 15 строк расписания и нарядов 2026 года.

## ADR-008 — Горизонт модели отдельно от представления

Статус: принято в ТЗ.

Решение: run имеет horizon day/month/year, UI — DAY/MONTH/PERIOD и опционально YEAR. Конкурсные 61 день хранятся как среднесрочный month-run. YEAR только scenario, с отдельными предположениями и выпуском.

Причина: график суток внутри month-run не должен незаметно менять модель. Произвольный период внутри ноября–декабря — обязательный сценарий.

## ADR-009 — Временная проверка важнее сложности модели

Статус: принято в ТЗ; модели ещё не реализованы.

Решение: обязательны сравнение сезонных baseline, Direct CatBoost, Daily TS и ансамбля, временные folds и WAPE. Веса выбираются на tuning folds, качество — на отмеченной исторической проверке. Лаги и профили не читают будущие факты.

Причина: notebook на другом датасете и случайное разбиение не доказывают качество двухмесячного прогноза. Более сложный ансамбль не обязан стать финальной моделью, если проигрывает компоненте.

## ADR-010 — Нормализация принадлежит backend

Статус: принято в ТЗ.

Решение: Q05/Q95 и производные поля рассчитываются при импорте по маршруту, сохраняются с run и версией источника истории. Frontend отображает значения, не считает квантили и не суммирует проценты по маршрутам.

Причина: одна шкала для API, карты и экспорта; проценты отражают распределение потока, а не физическую вместимость. [Backend §7](../spec/BACKEND.md#7-нормализация).

## ADR-011 — Frontend начинается независимо от готовности прогнозного API

Дата: 26.09.2026. Статус: выбранный порядок применяется; FE-01/02 реализованы и приняты, FE-03 реализована и ожидает ручную визуальную приёмку. Уточняет этапность DEV-08, не меняет ТЗ 4.2.

Решение: сначала создавать UI в `frontend/` через общий типизированный интерфейс данных с HTTP-адаптером и отдельным development/test fixture-адаптером. Режим выбирается явно через `VITE_DATA_SOURCE=api|fixtures`; default/production — api. Fixtures маркируются на экране как тестовые и не подставляются после сбоя HTTP. Production-сборка с выбранным fixtures запрещена.

Причина: API прогнозов пока отсутствует, но его контракт уже описан; frontend можно разработать и проверить без создания второго backend или изменения DTO. Fixtures — средство проверки UI, не предсказание модели и не доказательство работающей интеграции.

Следствие: FE-01 проверяет DAY конкретного маршрута и KPI, FE-02 добавляет MONTH/PERIOD/ALL и экспорт, FE-03 — карту, затем выполняется обязательная интеграционная проверка с настоящим run. DEV-01 сохранена отдельно; её выполнение перед UI не требуется, но она остаётся необходимой перед изменениями backend. Результаты FE-01–03 записаны в [журнале](CHANGELOG_AGENT.md), текущая карточка FE-03 — в [ACTIVE_TASK](ACTIVE_TASK.md) до ручной приёмки.

## Как добавлять новое решение

Добавь следующий ADR с датой, статусом, решением, причиной, последствиями и ссылкой на изменяемый контракт. Если он заменяет существующий ADR, укажи оба номера и пометь прежний заменённым. Не меняй API или набор обязательных компонентов только в этом журнале: обнови полное ТЗ и короткий SPEC.
