# Проверки разработки

Состояние на 26.09.2026: работает справочный backend; отдельного pytest-набора, frontend, Compose и миграций пока нет. Команды ниже разделены по доступности. Все команды запускаются из основного корня `MTTECH/`, примеры рассчитаны на PowerShell.

## 1. Доступно сейчас: проверка backend вручную

При первом создании окружения установи зависимости из корневого файла:

```powershell
python -m pip install -r requirements.txt
```

Не переустанавливай зависимости перед каждой правкой документации. В репозитории они пока не закреплены; фиксация совместимых версий — отдельная задача.

В одном терминале запусти сервер:

```powershell
python -m uvicorn app.main:app --app-dir web-forecast --host 127.0.0.1 --port 8000
```

Оставь его работать и во втором терминале проверь:

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:8000/health'
Invoke-RestMethod -Uri 'http://127.0.0.1:8000/api/routes'
Invoke-RestMethod -Uri 'http://127.0.0.1:8000/api/routes/number/1'
Invoke-RestMethod -Uri 'http://127.0.0.1:8000/api/stops'
Invoke-RestMethod -Uri 'http://127.0.0.1:8000/api/assignments?route_id=4450&date=20260208'
```

Ожидается: HTTP 200; health сообщает status/service; списки содержат count и данные; номер 1 соответствует GTFS route_id 4450. У текущего XLSX 10 справочных маршрутов, 489 остановок и 2 наряда после указанного фильтра. Числа описывают текущий файл, не универсальный контракт на будущие справочники. `/docs` можно открыть в браузере. Завершение сервера — Ctrl+C в первом терминале.

Сейчас `/api/forecast` и `/api/predict` не реализованы как работающие endpoint. Их недоступность не означает успешную приёмку продукта; ручная проверка выше проверяет только существующую основу.

## 2. Backend-тесты — после DEV-01

Следующие файлы/команды должна добавить задача DEV-01, сейчас их наличие не утверждается:

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest web-forecast/tests -q
```

Тестовые зависимости указываются явно; TestClient не должен случайно работать только из-за библиотек, установленных у одного разработчика. Результат фиксируется как фактические passed/failed/skipped и причина пропусков. «No tests collected» не равно «проверка прошла».

После SQL-этапа интеграционные тесты запускаются на отдельной тестовой PostgreSQL с миграциями. Не направлять очищающие fixtures на рабочую БД. Конкретную переменную URL и команду записать сюда вместе с реализацией; SQLite не подтверждает PostgreSQL-транзакции и ограничения.

## 3. Внешний POST — после реализации и публикации run

Предусловия: применены миграции, импортирован собственный модельный конкурсный прогноз, активный month-run покрывает 01.11–31.12.2025, backend готов. Пример не загружает новые факты и не запускает обучение:

```powershell
$predictPayload = @'
[
  {"route": 1, "date": "11/1/2025", "hour": 0},
  {"route": 1, "date": "11/1/2025", "hour": 1}
]
'@
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8000/api/predict' -ContentType 'application/json' -Body $predictPayload
```

Ожидается массив двух записей route/date/hour/prediction, с исходным порядком и строкой даты. Prediction берётся из модели; **349 не является обязательным ожидаемым значением**. Для получения HTTP-заголовков вместо Invoke-RestMethod можно использовать Invoke-WebRequest и посмотреть `X-Forecast-Run-Id`.

Полная проверка включает: ISO и MDY, повторы ключей, неподдерживаемый номер → 422, пустой массив → 422, неверный час → 422, один ошибочный элемент отклоняет весь batch, неизвестный явный run → 404, отсутствие опубликованного прогноза → 503. Границы размеров и остальные случаи — в [Backend §8.5](../spec/BACKEND.md#85-внешний-api-прогноза-по-списку-ключей).

## 4. Frontend — после создания frontend/package.json

Команды целевые: запускай их только после появления каталога, lockfile и указанных scripts. Если script называется иначе, обнови эту инструкцию по фактической реализации.

```powershell
Push-Location frontend
npm ci
npm run typecheck
npm run build
npm test
Pop-Location
```

Не заменяй отсутствующий lockfile случайной переустановкой: зависимостями занимается задача создания frontend. После сборки проверь в браузере маршрут 1, маршрут 17 без геометрии, ALL, ошибки API и период 15.11–05.12.2025: 504 почасовые точки маршрута или 5 040 для ALL. Карта, график и CSV закрепляют один run_id. Географический выбор не меняет количество посадок.

## 5. ML — после создания ml/src и тестов

Предполагаемая команда модульных проверок:

```powershell
python -m pytest ml/tests -q
```

Проверять parser маршрута/времени, target, сетку, отсутствие утечек, WAPE, доли HourShare и сохранение сумм. Затем выполнить CLI подготовки, backtest и predict из [ML-ТЗ §8](../spec/ML.md#8-реализация-и-интерфейс-команд). Это длительные профильные проверки, их не нужно запускать для каждого изменения документов или frontend.

Приёмка final submission: 14 640 строк данных, 10 маршрутов, все часы ноября–декабря, уникальные ключи, ISO, `;`, четыре колонки, конечные неотрицательные значения. Проверить факт происхождения от собственной модели и cutoff истории. Указать реальные метрики и покрытие, не объявлять скрытый score измеренным.

## 6. Compose и нагрузка — после инфраструктурного этапа

После появления `docker-compose.yml`, Alembic и Dockerfile:

```powershell
docker compose up --build
```

Миграцию выполнить способом, реализованным инфраструктурной задачей, до проверки readiness; этот README не предполагает, что compose автоматически запускает Alembic. Схема поставки содержит postgres/backend/frontend, ML training при старте web не запускается.

Locust запускается после функциональной приёмки по [Backend §11](../spec/BACKEND.md#11-проверки-и-поставка). Требуются реальные RPS/latency/error rate/CPU/RAM и отдельное измерение полного POST-batch. Не объявлять целевые p95 измеренным результатом.

## 7. Проверка изменений и документов

Для любой задачи:

```powershell
git diff --check
git diff --stat
git status --short
```

`diff --stat` не показывает неотслеживаемые файлы, поэтому status обязателен. Если рабочее дерево уже содержало изменения, в отчёте отдели свою задачу от прежних правок; не сбрасывай их.

Для Markdown проверь локальные ссылки/якоря, закрытые code fences, JSON-примеры, одинаковое количество ячеек таблиц и соответствие текущему ТЗ. Эти проверки достаточны для чисто документальной задачи; не запускай фиктивный build отсутствующего приложения.

## 8. Как записать результат

В CHANGELOG_AGENT укажи: команду, краткий результат, среду/данные при необходимости и то, что не проверялось. Если проверка заблокирована отсутствующей зависимостью или данными, это ограничение, а не passed. Укажи причину и следующий конкретный шаг.
